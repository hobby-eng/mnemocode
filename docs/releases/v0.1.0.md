First release of MnemoCode: offline, reversible representations of English BIP39 recovery phrases,
date-shift masking, Shamir shares and printable cards. The complete history is in
[CHANGELOG.md](https://github.com/hobby-eng/mnemocode/blob/v0.1.0/CHANGELOG.md).

## Distribution

- Each release has one executable file for Linux, Windows and macOS, with Node.js, the card artwork and the SSKR engine built in; `pnpm build:executable` builds it for the current computer.
- Started without a command in a terminal, for example by a double-click on the executable file, MnemoCode shows a menu. It asks step by step, with examples, and shows in grey the command that does the same before it runs it.
- Encode in the menu offers the usual sets of Shamir shares, such as 2 of 3 or 3 of 5, and any other up to 16 shares, and writes them in the form chosen: restoring them gives that form back. Entry 3 splits the seed phrase itself into standard SSKR shares in Bytewords or as a `ur:sskr` code.
- The menu checks each of its own answers at once, such as a file name, a file dragged into the terminal, a fingerprint, an address or a share count, and asks again with one line that says why. When a command stops unexpectedly, the menu offers to start it again with the same answers; after a failed self-test it no longer offers the entries that ask for a seed phrase or a share.
- `mnemocode <command> --help` explains every option of a command with examples; `-h` gives a short summary.
- Each part of the library, such as the date search, the share set or the wallet check, has an entry point of its own without Node.js code, such as `mnemocode/core/date-search`. Another program, a browser page for example, takes only the part it needs and passes what only it has, such as its PBKDF2 or its SSKR library. [Source layout](https://github.com/hobby-eng/mnemocode/blob/v0.1.0/docs/ARCHITECTURE.md#modules-for-other-hosts) lists the parts.
- Each executable comes with a file of license notices for Node.js and every library it contains, and a release draft is made only after the complete CI has passed.
- GitHub signs the build provenance of every release file: `gh attestation verify` shows that a download was built from this repository by its release workflow.
- The `SHA256SUMS` of every release is signed with the maintainer's OpenPGP key, fingerprint `28FC51B1DB80DF2101128CB30EDD4814591DD095`, which GitHub also shows at https://github.com/hobby-eng.gpg. A tag creates a draft release, which the maintainer checks and signs on their own computer with `scripts/sign-release.mjs` before publishing it with `SHA256SUMS.asc` and `RELEASE-SIGNING-KEY.asc`; [Releasing](https://github.com/hobby-eng/mnemocode/blob/v0.1.0/docs/RELEASING.md) describes the steps.

## Formats

- Numbered representations are now consecutive: `colors-unicode` uses `--format 4` instead of `--format 6`.
- `colors-unicode` is written as four-digit codes instead of Private Use symbols, which many programs could not show. The symbol form can still be decoded.

## Recovery

- Shares with unreadable elements can still be used: mark each with `?` at its place, on any of the shares, such as two words on each of three shares. MnemoCode repairs all of them together: the checksums, the data the shares have in common and every share beyond the threshold settle most marks without trying anything, and the SSKR secret digest decides the rest. Before any search it shows how many combinations are open, how long they take, and which element or how many more shares would settle them; a search longer than 12 hours is asked for first, or needs `--max-tries`. In colors and Unicode codes written apart, a `?` inside a code stands for one unreadable digit, such as `#B5?0??` or `4E?0`, and the digits read are used: those of a color as bits, those of a Unicode code by trying each word whose code fits. Every phrase that passes is listed with its fingerprint, never chosen, and a wallet check keeps the matching one. `sskr-combine` names every filled-in element, by share and place, so that the written copy can be corrected. Entry 5 of the menu and `sskr-export` give the repaired shares back whole, in their own form, without showing the phrase.
- `recover-word` finds several forgotten words, written as `?`, a beginning such as `ab*`, or a few words such as `rich|rice`, up to 16,777,216 combinations, and with `--missing-word` a word missing at an unknown place. Every candidate is checked offline against a wallet check when one is given.
- `recover-word`, `recover-date` and `sskr-combine` save their candidates with `--candidates-file` as a [candidate list](https://github.com/hobby-eng/mnemocode/blob/v0.1.0/docs/CANDIDATES.md) for the Discovery Scanner of the multi-chain wallet tools: encrypted with age to the one-time key the Scanner shows, or with a passphrase; without encryption only with `--plaintext-candidates`. Entry 5 of the menu offers it. The search, the list and its encryption are host-neutral modules that the Wallet Deriver and the Scanner compile unchanged.
- The master fingerprint and the other wallet checks compute the BIP39 seed with Node's own PBKDF2, about seven times faster, with the same result.
- Every wallet check also takes an address of another coin, the coins of mhfe on their standard paths: Bitcoin Cash, Cosmos, Dash (also Platform), Dogecoin, Ethereum and EVM networks, Ethereum Classic, Injective, Litecoin, Tron, XRP and Zcash (transparent). `--coin-address` with `--coin` gives it from the command line; in the menu, "Address of another coin" asks which coin, then its address. The library part `mnemocode/core/coins` reads and checks them for another host; `mnemocode/core/coin-address-evidence` checks an address of one coin given itself, so that a host of one coin, such as the Deriver's Dash edition, takes that coin's module alone.
- An address, a public key or a WIF is compared with the first 20 addresses of the wallet, from `--index` on, so that it need not be the first one: `--scan-gap N` sets how many, up to 1000, and the menu asks after the address, Enter for 20. The library takes the count as `addresses` in the evidence.
- Every answer of the menu that is no secret can be given as an option of its command. New options: `--scan-gap`; `--max-candidates` for `sskr-combine` and `sskr-export`; `--backup-check yes|no` for `encode` and `sskr-split`, which also takes `--heir-sheet` and `--heir-sheet-size` now; for `decode --ask-secrets`, the wallet options with `--bip39-passphrase-file`, `--encoded-fingerprint`, `--list-candidates`, `--max-candidates`, `--max-results`, `--max-tries` and `--input-kind codes|share`. A share typed into Decode takes Decode's wallet and limits to the restore. The menu's own wallet question offers every coin and the number of addresses too.
- Every feature has its self-test beside it: quick known answers before every command (BIP39 seed and master fingerprint, date patterns, codes and shares marked with `?`, the word search, the candidate list, wallet evidence and the address scan, coin addresses, the heir sheet, share cards), and its row in `mnemocode self-test` with the slower checks (the 24 English BIP39 vectors, date and word searches with a wallet, age-encrypted lists, share backup checks, shares repaired together and with dates, the heir-sheet and share-card PDFs, QR images beside a sheet). Known answers come from published vectors or from an independent implementation that first reproduces one, and every check also gets a case it must refuse. The checks before every command take about a third of a second: the valid last words of a phrase are now found from its entropy, without validating 2,048 phrases.
- `MnemoCodeSelfTest` takes the checks of the features a host builds in (`features`, `MnemoCodeSelfTest.core(features)`) and optionally the host's PBKDF2.
- Share cards print a share in the form it is written in: word numbers, Unicode codes or Bytewords, three to a card, beside colors drawn at random that only decorate them; a share in colors prints its colors, as before. The menu offers printable cards with a choice of design for shares in every form; before, shares in word numbers came out as cards of the default design that printed colors. For printable cards it asks the kind of file (PDF, PNG or JPEG) first, then the layout (A6 sheets, A4 sheets or separate business cards), so that images of A4 sheets can be chosen too.
- A date search finds each phrase once. Seedshift adds the year to a word number modulo the 2,048 words, so a forgotten year found the same phrase with the year 2,048, 4,096 and 6,144 years later too, as several results; now each set of shifts is tried once, with the earliest dates, which also makes a search of a whole year about five times shorter. Several phrases restored from shares are numbered "phrase 2 of 3" and, on the private screen, shown one screen each, the next on Enter. A record of the Original Seedshift with a replaced last word finds its 128 or fewer last words from the entropy rather than by trying all 2,048, about seventeen times faster.
- In the card design "Signature curves" the company name stands above the logo, which moves down: lower, the curve ran under the name.
- In the menu, finding a forgotten date digit asks how to recognise the wallet: by its fingerprint, a Bitcoin address or an address of another coin, and after an address among how many to look; with the Original Seedshift it may be left out. `recover-date --ask-secrets` asks for it after the dates when the mode needs one and no option gives it.
- Decode and Restore from Shamir shares take `?` for a forgotten digit of a date on the private screen, in Restore also together with `?` in share codes, and search the dates as `recover-date` does. Where every date gives a valid phrase they ask for the wallet's fingerprint or one of its first receiving addresses, and Restore shows the share and date combinations and their time before it searches. Decode asks for the wallet with the original Seedshift too, where it may be left out.
- On the private screen, Decode, the search for a forgotten date digit and Restore from Shamir shares show the encoded fingerprint, the fingerprint of the masked phrase that Encode and the split print, as soon as the codes or complete shares are read: a code written down or typed wrongly shows before the dates are typed. Encode and Decode show it by one rule: whenever the codes are a valid BIP39 phrase, which the Original Seedshift's are only by chance.
- On a terminal, the result of Decode and of Restore from Shamir shares gets a screen of its own: the questions and the search are cleared away, and each part stands apart under its label. The original seed phrase is numbered, four words to a row as `mhfe` shows a phrase, with a line to copy below it, and each fingerprint stands under the phrase it belongs to: the encoded one under the masked phrase (decoy), the original one under the seed phrase. Restore lists the elements it filled in as a table, a row for each share, and the progress of a search stays on one line.
- On the private screen, `decode` asks for codes without an MNC1 header whether Seedshift was used and which one, and `recover-date` which Seedshift; Decode in the menu passes the answer on as `--mode`.
- When nothing tells which of two shares is wrong, such as two that carry the same share number but differ, both are named and the person chooses which to change or leave out. The written-backup check uses a share given twice once, as Restore does.
- `recover-date` accepts `?` for each forgotten digit and up to three incomplete dates. Identical patterns are not tried twice, and a limit stops a search that is too large before it starts. Every search of the dates or of marked shares that takes longer than 12 hours on the computer is asked for first; `--max-candidates` and `--max-tries` allow one from the command line.
- Decode takes codes with `?` where they cannot be read, on its private screen: a word number, a word, a Unicode code or a whole color, narrowed by a few letters (`ab*`), words joined by `|`, or a `?` for one digit. It finds them by the encoded fingerprint that Encode showed, without the dates; by the wallet's fingerprint or an address with the dates, which may hold `?` too, so that codes and dates are found together; or lists them where they are few. It says how long the search takes, and shows the codes and dates it found.
- A Shamir share typed into Decode or read from a QR code, complete or with `?`, is recognized: Decode goes on to the restore from shares with it as the first share and asks for the others; a share read from a QR code is shown as text, and the next can be read from another QR code image. Where the text could also be the codes, it asks which.
- A date to search may hold a lone `?` for a whole day, month or year (`15-?-2025`), or for a whole date not remembered at all; a few values joined by `|` (`05|15-09-2026`). A search may have up to 2,147,483,648 date combinations; one longer than 12 hours is asked for first.
- Added `recover-word`. It lists the words that can replace forgotten words and marks the candidates that match a known detail of the wallet. With `--legacy-valid-last-word` it lists the valid last words of a legacy phrase.
- After Encode shows its result on the private screen, it offers to check the backup: you type it again from what you wrote down, with the dates, and MnemoCode says whether it restores the same seed phrase.
- `encode --heir-sheet` saves one sheet for heirs, to print on both sides in A5 or A6 (`--heir-sheet-size`): what the backup is, room for a hint written by hand, the steps in the menu, and the basics for someone new to wallets. It holds no secret: no codes, no dates, no fingerprint and no places. [A guide for heirs](https://github.com/hobby-eng/mnemocode/blob/v0.1.0/docs/HEIRS.md) explains the same in more detail.
- A date needs a four-digit year. `23-09-26` was read as the year 23 and is now an error.
- A record header whose version is written with leading zeros, such as `MNC01:`, is refused instead of being read as `MNC1:`.

## Secret handling

- MnemoCode clears its temporary copies of the phrase data after use.
- Nothing is saved over an existing file or folder. When the name given is taken, MnemoCode saves under the first free numbered name, such as `cards-1.pdf`, without spaces or brackets that a shell would read, and says so after saving; the name is settled before the seed phrase is asked, so a taken name no longer stops a command. A result named like an input of the same command is still refused.
- A file with Shamir shares now appears under its name only when it is complete, as the other exports already did. MnemoCode writes it to a private temporary file first and then gives it its final name in one step, without ever replacing an existing file. On memory cards and USB sticks formatted with FAT or exFAT, which cannot give a file a second name, an empty file holds the name until the complete one replaces it, and is removed again if that fails.
- Text, standard input and QR image files are read up to their size limit and no further, also when they come from a pipe or keep growing, instead of trusting the size the system reports.
- A typed answer can be edited as in a shell: the arrow keys, Home and End, Ctrl with an arrow, Delete, Ctrl+K and Ctrl+W, also when a long answer wraps onto further rows. Escape alone no longer swallows the next key at a prompt for a secret.
- `--ask-secrets` works on Linux, macOS and Windows: MnemoCode reads the answer itself instead of through `systemd-ask-password`, which exists only on Linux. Backspace and Ctrl+U edit it. Keys typed or pasted before a question appears do not answer it. A paste of several lines is one answer: words, codes and dates may come one per line, and shares pasted one per line count as separated by semicolons. A wide character at the right edge wraps onto the next row as the terminal wraps it.
- No command ends because of a wrong answer. On the private screen each answer is checked as soon as it is given, and what can be checked before the dates, such as the record header, the mode, the form and the checksum, is checked before they are asked. An answer that cannot be used is explained in one line that names at most its place, such as "Date 2" or "Share 3", and asked again; the other answers are kept. A share that cannot be read is typed again alone, and an empty answer is asked again with a hint. A result that cannot be used, such as dates that give no matching wallet or shares that restore nothing, offers what to change. Only the person ends a command early, with Ctrl+C ("Cancelled.", exit code 130) or by choosing Stop, apart from a failed self-test; Escape does nothing while an answer is typed.
- When a file cannot be saved after the result is shown, for example on a full disk, the result stays on the private screen, one line says why, and MnemoCode offers to try again, to use another name, or to skip it. Shares are shown even when saving them fails, and the passphrase of a candidate list is asked again, without a limit, until both entries agree.
- A command that asks for a secret runs on a private screen of its own in the terminal: what you type is shown there, and so is the result. When you press Enter, the screen is cleared, so that nothing stays in the scrollback; output sent to a file or a pipe goes there as before.
- With `--ask-secrets`, `decode` and `recover-date` take the record from `--input-file` or `--qr-file` and ask only for the dates.
- Shares can also be written in Bytewords, the standard long form in words (`--share-format words`), as other SSKR tools write them, and, for MnemoCode only, as word numbers, Unicode codes or colors as Unicode codes (`indexes`, `unicode`, `colors-unicode`). A share file saved with `--output` holds the shares in the format shown, and `sskr-combine` shows the restored backup in the form of the shares. `encode --sskr` shows the whole phrase beside the shares only with `--format`.
- Every run is protected as far as Node.js allows: core dumps are off on Linux and macOS, and MnemoCode runs under the Node.js permission model. That model allows no network, and a command that does not need them cannot write files or start other programs. The single executable starts under the model by itself, and each entry of the menu runs in a process of its own. A caller that already runs MnemoCode under that model keeps the rights it granted on purpose, such as `--allow-net`. The library has the rights of the program that uses it. Node.js enforces the model, not the operating system, so it is not a sandbox.
- Before a secret, MnemoCode warns when swap is not encrypted (Linux) and when a file would be saved into a folder that a cloud service synchronises.
- On Linux the temporary files of PNG and JPEG export stay in memory (`/dev/shm`).
- The folder that holds the separate cards of one Shamir share can be read only by your user account, like the other export folders.

## Card exports

- The QR code that `--card-qr` prints on the sheets is also saved as a PNG image where they go: beside the PDF, or in the folder of the images or card files, one image per share for Shamir shares. Decode reads it back with `--qr-file`, Restore with `--share-qr`.
- Every collection, including A4, is one page laid out as a design proposal.
- A collection sheet has a centred heading and the slogan in the bottom line. Business cards lie on a dark page with a grey world map, light cards on a light one, and material samples on a backdrop of their own setting.
- A material sample shows a colour that the material is really made in, near its reference, laid over the photograph. Two different codes never get the same sample on one sheet.
- The optional QR code of a collection has its own corner on the same page. No separate QR page is made.
- Individual cards have no QR code.
- In the menu, "Also as printable cards" asks how to save the cards: one PDF of A6 or A4 sheets, separate business cards in a new folder as PDF, PNG or JPEG, or images of the sheets as PNG or JPEG; it says at once when images need `pdftocairo` and it is missing. For sheets it asks whether to add a QR code with all the codes of the sheet, and for all cards whether to type your own details. The names and details on cards are a decoy, random unless typed.
- `--page-size business` gives separate numbered cards, one per page. `a6` and `a4` give one sheet, and `a6` is the default for every template. The `wallet` size is removed.
- Images are made with the Poppler program `pdftocairo`. The rounded corners of a separate card are transparent in PNG.
- Separate business cards print their number and the size of the set before the code.
- Invented email and website addresses end in `.example`, so they cannot belong to a real company.
- `--cards-dir` is refused together with a sheet size.
- Each Shamir share has its own page, and a QR code holds exactly one share.
- Other programs can render the same cards through the `mnemocode/cards` entry point, which has no Node.js dependency. A card session keeps the same invented person, company and studio for every export of one working session.
- Text on business cards is aligned with its icon or logo, and a role no longer touches the name above it.

## Toolchain and dependencies

- The development runtime is Node.js 26.10.0.
- Updated the npm dependencies, including Vitest 5.0.3 with its V8 coverage provider, TypeScript 7.0.2, Prettier 3.9.9, tsx 4.23.15 and `@types/node` 26.6.4.
- The SSKR engine is built here from its Rust source, offline in a pinned container (`pnpm build:sskr`), with Rust 1.99.0, wasm-bindgen 0.2.129 and current crates. A release builds it again and checks that the bytes are the same.
- Pinned pnpm 12.8.1, which also records its own release in the lockfile. A toolchain check makes CI read the Node.js version from `.node-version` and the pnpm version from `package.json`.
- The npm package includes the guides for shares, cards and the source layout.
- `pnpm check` also refuses a blank line inside a Markdown list, which GitHub renders with wider spacing than other lists.
