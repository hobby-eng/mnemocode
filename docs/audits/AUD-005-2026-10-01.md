# AUD-005 — Full-scope MnemoCode audit after the executable release work

Twelve confirmed findings, all low; none critical, high or medium. The transformations, records, recovery checks and SSKR agree with an independent oracle, the published vectors and every documented example that was run. The defects are in the boundaries around them: the release path, legal notices of the executable, hidden input on Windows and macOS, two lenient decoders, folder permissions, help layout, untested integrity gates and stale documents. This is a bounded audit of one identified snapshot, not a guarantee that defects are absent.

## Review evidence

### Scope and methodology

Everything the snapshot supports was in scope: the five representations and three transformation modes plus legacy-valid recovery, MNC1 records, date and word recovery with local Bitcoin evidence, SSKR split/combine/export with its color and Bytewords transport and the vendored WASM integrity gate, card PDFs, QR output and input, image export, secret input and output paths, the new terminal and help code (3a86e72), the single-executable build and its workflow (d4be791, 8c427af), dependencies, CI and every user document. The audit traced each input to its output in the source and then ran the production entry points with public data.

Environment: Linux 7.0.0 x86_64 (glibc 2.43), Node.js 26.10.0, pnpm 10.19.0, Python 3.14.4, Poppler `pdftocairo` 26.01.0, esbuild 0.28.2, Vitest 5.0.3. ### Findings

#### AUD-005-SEC001 — Low — SSKR fragment folders are created with the default folder mode

- **Category:** SEC
- **Severity:** low
- **Status:** open
- **Release blocking:** false; the parent export folder is private, so no other account can reach the files while they stay inside it.
- **Affected files and builds:** `src/export/sskr-cards.ts:134` (`mkdir(folder)`), all builds.
- **Reproduction:** `sskr-export --share-file <one official share> --cards-dir NEW --page-size business` under `umask 022`; `defect-probes.mjs` checks the mode of `NEW/collection-…`.
- **Expected behavior:** Like every other export folder (staged with `mkdtemp`, mode 0700), the folder that holds one share's cards is private.
- **Observed behavior:** The per-share folder has mode 0755 (umask-dependent; 0775 under umask 002). Files inside are 0600.
- **Impact:** Once a user moves a share folder out of its private parent, as the program advises ("store different shares separately"), other local accounts can list it. File names carry each card's first reference code, a few bytes of one share. No file content is exposed.
- **Evidence:** Local: `AUD-005-evidence/defect-probes.log`; `AUD-005-harnesses/defect-probes.mjs`.
- **Recommended fix:** Create the folder with mode 0700.
- **Required verification:** A test checks mode 0700 of a share folder on POSIX; SSKR export tests stay green.

#### AUD-005-API001 — Low — The record header accepts non-canonical version numbers

- **Category:** API
- **Severity:** low
- **Status:** open
- **Release blocking:** false; MnemoCode writes only `MNC1:`.
- **Affected files and builds:** `src/record.ts:27-28` (`/^MNC(\d+):…/`, then `Number(match[1])`).
- **Reproduction:** `parseRecord('MNC01:direct:english:abandon … about')` and `parseRecord('MNC0001:…')`.
- **Expected behavior:** README documents the header `MNC1:<mode>:<format>:<data>`; the guide asks that malformed input is not silently normalized.
- **Observed behavior:** Both return a version-1 record.
- **Impact:** A damaged or foreign header is read as a valid record instead of being reported. Decoding still validates the payload, so no wrong phrase was produced.
- **Evidence:** Local: `AUD-005-evidence/defect-probes.log`.
- **Recommended fix:** Accept only a version number without leading zeros; keep `Unsupported MnemoCode record version` for other numbers.
- **Required verification:** `MNC01:` and `MNC0:` are malformed, `MNC2:` is unsupported, every record MnemoCode writes still parses; MNC1 output unchanged.

#### AUD-005-API002 — Low — Legacy-valid decoding reports invalid indexes as a checksum failure

- **Category:** API
- **Severity:** low
- **Status:** open
- **Release blocking:** false; the call is still refused.
- **Affected files and builds:** `src/core/seedshift.ts:211-219` (`decodeIndexesLegacyValid`), public library API.
- **Reproduction:** `decodeIndexesLegacyValid([2048, 0, …], [01-01-2000])`; also -1 and 1.5.
- **Expected behavior:** As in `decodeIndexes` and `decodeIndexesLegacy`: `Every BIP39 index must be an integer from 0 through 2047.`
- **Observed behavior:** `The legacy valid-last-word container has an invalid BIP39 checksum.` The invalid index is looked up as `undefined` in the word list.
- **Impact:** A library caller is sent to look for a damaged record instead of a programming error. The CLI parses indexes first and is not affected.
- **Evidence:** Local: `AUD-005-evidence/defect-probes.log`.
- **Recommended fix:** Validate indexes in all three decoders through one shared check.
- **Required verification:** Regression test for 2048, -1 and 1.5; legacy-valid recovery vectors unchanged.

#### AUD-005-BLD001 — Low — A version tag publishes executables without the test suite or a version check

- **Category:** BLD
- **Severity:** low
- **Status:** open
- **Release blocking:** false for this snapshot (no tag exists); it guards every future release.
- **Affected files and builds:** `.github/workflows/executable.yml` (`release` needs only `build`), `.github/workflows/ci.yml`.
- **Reproduction:** Static review. The tag push starts CI and Executable as separate workflows; `release` waits only for the three `build` jobs, which run `build-executable.mjs` and `verify-executable.mjs` (self-test and four smoke checks) but not `pnpm check`, `pnpm test`, the card round trip or `pnpm audit`. No step compares the tag with `package.json`.
- **Expected behavior:** The guide asks that mandatory verification cannot be bypassed by the normal release path, and that tag and version agree.
- **Observed behavior:** A tag on a commit whose test suite fails still publishes; a tag `v0.2.0` on version 0.1.0 publishes `mnemocode-0.1.0-*` files as "MnemoCode 0.2.0".
- **Impact:** Release correctness depends on the publisher checking CI by hand.
- **Evidence:** `.github/workflows/executable.yml` at the reviewed commit.
- **Recommended fix:** Make the CI workflow callable and require it, and a tag/version check, before `release`.
- **Required verification:** Workflow syntax check; the dependency is visible in the workflow; observed on a real tag only by the maintainer.

#### AUD-005-BLD002 — Low — Executable releases carry no license notices for Node.js and the bundled packages

- **Category:** BLD
- **Severity:** low
- **Status:** open
- **Release blocking:** false; a legal-compliance gap, not a functional one.
- **Affected files and builds:** `scripts/build-executable.mjs`, `.github/workflows/executable.yml` (publishes only `mnemocode-*` and `SHA256SUMS`), every executable.
- **Reproduction:** `bundled-licenses.mjs` lists 17 npm packages bundled by esbuild (among them jsQR under Apache-2.0, pako, tslib, @noble/*, pdf-lib) and finds no notice file next to any executable. The executable also contains the Node.js runtime and the SSKR WASM built from BSD-2-Clause-Patent crates.
- **Expected behavior:** MIT, Apache-2.0 and BSD-2-Clause-Patent require their notices with binary redistribution; `THIRD_PARTY_NOTICES.md` covers neither Node.js nor several of these packages.
- **Observed behavior:** A release holds three executables and `SHA256SUMS` only.
- **Impact:** Redistribution without the required notices; no effect on function or secrets.
- **Evidence:** Local: `AUD-005-evidence/bundled-licenses.log`.
- **Recommended fix:** Build a notice file per executable from the bundled packages' own license files, Node.js's `LICENSE`, the project and SSKR notices, and publish it with the executable.
- **Required verification:** `bundled-licenses.mjs` passes on a fresh build; `verify-executable.mjs` checks the file.

#### AUD-005-BLD003 — Low — The executable check fails when the release folder holds the other systems' files

- **Severity:** low
- **Status:** open

#### AUD-005-BLD004 — Low — The card check scripts write PDFs into a folder that Git does not ignore

- **Status:** open
- **Release blocking:** false.
- **Affected files and builds:** `scripts/check-card-output.mjs:17`, `scripts/business-goldens.mjs:8` (default `goldens/…`), `.gitignore`.

#### AUD-005-BLD005 — Low — No test covers the SSKR integrity gate or its manifest

- **Category:** BLD
- **Severity:** low
- **Status:** open
- **Release blocking:** false; the gate works today.
- **Affected files and builds:** `src/sskr/runtime.ts:18-27`, `vendor/sskr/integrity.json`, `test/`.
- **Reproduction:** `git grep 'SSKR dependency integrity' -- test` finds nothing; no test compares the five non-runtime manifest entries (Rust source, Cargo files, declarations) with their files.
- **Expected behavior:** The integrity gate the security guide relies on, and the manifest the vendoring rule compares against, are kept by tests; a vendored refresh that forgets the manifest fails.

### Informational observations and recommendations

#### AUD-005-API003 — The JSON output names every result a date shift

`formatEncoded(result, 'json')` writes `"algorithm": "Seedshift-compatible date shift"` for direct, checksum-valid and legacy results alike. The form is reachable only from the library. Changing the string would change an encoded output, which this remediation must not do, so it is deferred; a later format version could name the mode.

#### AUD-005-API004 — Ordinary exports replace an existing file, Shamir exports never do

`encode --output/--pdf/--qr` and `preview --pdf` replace an existing file through a private rename; the `encode` help says so. SSKR record and PDF exports refuse an existing file. Both behaviors are deliberate and documented in the help; the README examples say "a new file". Recorded as accepted design; the README now states the rule.

#### AUD-005-BLD006 — Workflow and asset hygiene

`ci.yml` checks out with persisted credentials (the executable workflow does not); `executable.yml` pairs `upload-artifact` v7.0.1 with `download-artifact` v4.3.0. PDFs keep their creation and modification dates. The executable embeds every file under `assets/`, including the CJK font subset that no template uses yet and the map source of a generated module. None of this is a demonstrated defect; each is a candidate for a later cleanup.

### Assessment and limitations

The transformations, recovery, records and Shamir shares behave as documented and as the independent oracle predicts on every executed case. The findings concern release process, packaging, platform messages, input strictness, folder permissions, help layout, test coverage of the integrity gate and stale text. None of them changes a phrase, a record or a share.

- Linux x86_64 only. The Windows and macOS executables and the CI jobs were not run; their behavior is inferred from source and workflows.
- No Docker: the canonical SSKR WASM rebuild was not repeated; hash equality with the AUD-004 rebuild is the evidence.
- No real hidden-prompt session, physical print or scan, assistive technology, or RustSec scan.
- The oracle's color and color-Unicode packing re-implements documented rules; only the BIP39 list and the Seedshift construction are fully independent of the code.
- No release approval and no independent cryptographic certification.
