# AUD-011 — Targeted MnemoCode architecture and duplication audit

The current source contains **89 consolidation groups covering 109 scoped rules in 298 rule/site pairs**. These are low-severity maintenance findings, including small policy/text repetitions; they are not 89 independent security failures. Two bounded probes demonstrate actual acceptance/diagnostic differences. No production source was changed.

## Recommended fix order

1. First align known decimal-token acceptance and correct lexical cloud-path containment. Both differences were reproduced with bounded synthetic probes. (AUD-011-ARC001, AUD-011-ARC062).
2. Give supported BIP39 sizes and their derived widths one lightweight owner; reuse its values in core and front ends while retaining checks at trust boundaries. (AUD-011-ARC019).
3. Share SSKR framing and group/topology facts. Preserve distinct duplicate policies, recovery confirmation and secret cleanup; verify each extraction with focused regression cases. (AUD-011-ARC024, AUD-011-ARC028).
4. Consolidate card-content construction and private-directory publication, then the remaining rendering and CLI helpers. Use the detailed finding list below to keep each change small and reviewable. (AUD-011-ARC072, AUD-011-ARC083).

These are proposed changes; all findings remain open. This audit changes reports and harnesses only.

## Review evidence

### Scope and methodology

User corrected the target to MnemoCode. Targeted source audit of repeated rules, SRP/OCP/ISP/DIP and module extraction: 188 TypeScript/tooling files (38,328 lines; generated map/wordlist excluded), plus the SSKR Rust wrapper and static workflow/package/doc boundaries. This is not a full-scope security audit or release verification. No production fixes, commit, push or remote actions.

The four scopes were reviewed in parallel without edits or full tests. The coordinator reconciled overlapping claims and challenged security-boundary, framing, topology, algebra and geometry similarities. Only first-party current source and active consumers were counted. All figures below use the final coordinator catalog, not preliminary reviewer totals.

An implementation site is a separately written rule body, policy declaration or primitive route. Calls/imports and a helper plus its callers are not extra copies. Multiple expressions inside one owning validation pipeline are one site where specified; GF(2) explicitly counts five written reduction bodies. Distinct subrules of one root cause are cataloged separately. Rule/site pairs can share a source line when that line declares several different rules; 298 is not a count of distinct physical lines or files. **189 surplus sites** is arithmetic (298 − 109), not a measured amount of code that can safely be deleted.

### Why the current gates do not catch this

`test/portable-modules.test.ts` enforces imports, host neutrality, permitted packages, entry exports and declared composition. `test/one-coin-builds.test.ts` enforces selected-coin exclusion. Both pass (85 tests). Their assertions do not establish that two functions implement the same policy only once. Existing functional tests can pass while independently written paths currently agree. Written OOP rules require an ownership review in addition to these gates.

### Reproduced differences

- **AUD-011-ARC001:** the full numeric reader accepts `0001`; marking another of the twelve positions with `?` makes the marked reader reject that same known token. Replacing `0001` with `1` succeeds. The probe only parses; it does not enumerate candidates.
- **AUD-011-ARC062:** `cloudServiceOf` with an explicitly supplied synthetic OneDrive root recognizes `notes/export.txt` but misses `..notes/export.txt`. Its lexical containment copy tests a string prefix rather than a parent path component. No upload or real private data was involved.
- The runtime graph retains one CLI SCC: `input → ask → bitcoin-options → input`. A leaf bounded text reader can break it. No module-load failure is claimed; template-family and EncodeOutcome lexical cycles vanish after type erasure.

### Exclusions and skeptical decisions

- Exact public fixtures in separately selectable self-tests and independent literal vector/oracle expectations are not production duplication.
- Generated WASM/glue, extracted wordlists/map data and upstream internals are excluded.
- Validation/metadata erasure/entropy cleanup at independently callable boundaries is necessary. The shared rule body can move without removing any invocation.
- The SSKR coordinate-duplicate policies differ intentionally. The original duplicate-compatibility allegation was narrowed to shared identity/partition/threshold facts.
- Surplus-share confirmation is narrowed to substitution-window planning. Keep recovery library confirmation and cleanup at both boundaries.
- GF(2) totals count five reduction bodies in four owner functions; they do not count five complete solvers.
- MNC1 version membership and current engine capability catalogs can intentionally diverge. They are excluded from the confirmed catalog; current raw-format views are counted independently of the pinned record-version policy.
- BIP39 secret widths are counted once across core and SSKR; CLI BIP32 boundary ownership is merged into the core boundary rule.
- The 90 x 50 mm literal-bearing sites describe physical pages, design coordinates and drawing boxes. Four sites alone do not prove four interchangeable policy owners, so geometry is an uncounted contract-dependent suggestion.
- AUD-003-ARC001 concerned forward RGB-to-HSV, MM and full page tables. Forward HSV and MM remain shared; no recurrence is established. Current reverse HSV-to-RGB is a different algorithm.
- Artwork caches, generic secret/menu retry state machines, filename similarity, ceil-division expressions and raw-terminal listener/cleanup resemblance are not counted without a demonstrated common contract.
- Type-only template and EncodeOutcome cycles disappear after erasure. Facades and compatibility functions that delegate are not dead code or duplicate implementations.
