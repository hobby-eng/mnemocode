### Findings

#### AUD-018-SEC001 — Low — A QR image read as secret input leaves its file bytes and decoded pixels unwiped

- **Category:** SEC.
- **Severity:** low.
- **Status:** fixed (see the remediation addendum).
- **Release blocking:** false; Low: needs access to the process memory; the decoded text itself cannot be wiped in JavaScript.
- **Affected files and builds:** src/cli/qr-input.ts (decodeQrPngFile); src/cli/input.ts (--qr-file); src/cli/sskr-restore-command.ts (--share-qr); src/cli/share-repair.ts; src/cli/date-search.ts.
- **Reproduction:** docs/audits/AUD-018-harnesses/probes.ts, first case: the public record MNC1:direct:indexes with eleven 1s and a 4 (abandon … about) is saved with exportQrPayload and read with decodeQrPngFile; the bytes that readFileOrRefuse hands over and the RGBA data that pngjs decodes are captured.
- **Expected behavior:** bounded-read.ts: "the one copy returned is the caller's to wipe"; SECURITY.md: temporary copies of the phrase data are cleared as far as possible. The text reader does so (input.ts decodedText), as the probe's control shows.
- **Observed behavior:** After a successful read both buffers still hold their content: fileWiped false, pixelsWiped false. The control (readBoundedTextFile) wipes its bytes.
- **Impact:** An encoded record or a share given as a QR image stays in the heap as PNG bytes (up to 16 MiB) and as decoded pixels (about 2 MB for a 720-pixel code) until the memory is reused. Core dumps are off and the permission model applies, so reading it needs access to the process memory, swap or a hibernation image. jsQR's own working copies and the decoded string cannot be wiped.
- **Evidence:** AUD-018-evidence/probes.log (local), probes.command.json exit 1.
- **Recommended fix:** In decodeQrPngFile, wipe the file bytes and image.data in a finally block, on success and refusal alike, as decodedText does for text; add the probe as a regression test.
- **Required verification:** The probe's first case passes; the QR tests and the CLI self-test still pass.
