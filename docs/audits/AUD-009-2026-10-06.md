### Findings

#### AUD-009-FUN001 - Medium - Caller-owned dates can alter checked state and falsely approve an SSKR backup

- **Category:** FUN.
- **Status:** fixed.
- **Release blocking:** true; False approval of a backup contradicts a core recovery guarantee; resolve before publishing the new library API..
- **Affected files and builds:** `src/core/date-search.ts:111`, `src/core/date-search.ts:185`, `src/core/backup-check.ts:268`, `src/core/backup-check.ts:526`, `src/core/backup-check.ts:621`; exported Node/browser-host API
- **Reproduction:** Mask public abandon ... about at 23-09-2026, split 2-of-3, construct ShareBackupCheck with a retained date object and confirm restores. Change that object to day 24; checking the same shares with 24-09-2026 still reports restores although actual recovery produces a different phrase. Separately retain a DatesAnswer pattern and expand its arrays after construction: existing DateSearch grows from 365 to the 10,000,001 hard-limit sentinel and starts work. The harness stops at first progress, not a giant search.
- **Expected behavior:** Objects own an immutable validated snapshot; backup approval corresponds to actual reconstruction and searches cannot exceed validated limits through caller mutation.
- **Observed behavior:** Outer arrays are copied or frozen but nested dates/pattern arrays alias caller data. ShareBackupCheck caches held material before mutation and later compares changed dates without final recovered-phrase comparison.
- **Impact and limits:** Supported library callers can receive false backup assurance or start work beyond the checked limit. No current CLI false-pass, remote exploit, secret theft or giant search was demonstrated. EncodedBackupCheck baseline dates mutate too, but its full check has a recovered-result comparison; do not extrapolate the SSKR false-pass to it.
- **Evidence:** core-invariants.log: date ownership, pattern expansion and first-progress sentinel; sskr-boundaries.log: actual production WASM and mismatching recovered mnemonic.
- **Recommended fix:** Deep-copy and freeze date/pattern graphs at ownership boundaries, return independent immutable values, and retain the validated snapshot throughout search and backup checking.
- **Required verification:** Retained input and getter mutation cannot change state; original-date SSKR backup restores and wrong-date backup fails; compare actual recovery; attempted post-construction limit expansion cannot start work.

#### AUD-009-API001 - Low - DatesAnswer.of accepts invalid calendars and empty search patterns

- **Category:** API.
- **Status:** fixed.
- **Release blocking:** false; bounded constructor-contract failure without demonstrated incorrect recovered wallet.
- **Affected files and builds:** `src/core/date-search.ts:162`; exported Node/browser-host API
- **Reproduction:** DatesAnswer.of accepts {year:2026,month:2,day:31}; it also accepts a pattern with years:[], months:[1], days:[1]. Equivalent parsed input rejects these cases.
- **Expected behavior:** The typed public constructor preserves the documented searchable invariant and validation equivalent to parsing.
- **Observed behavior:** Only outer nonemptiness and work limits are checked; invalid complete dates and zero-candidate patterns become constructed objects.
- **Impact and limits:** Bounded exported-library contract failure. Invalid calendars generally fail later in normalization; empty patterns yield no work/no matches. CLI string parsing is not shown affected; no wrong wallet result is demonstrated.
- **Evidence:** core-invariants.log: missing expected exceptions for calendar and empty pattern.
- **Recommended fix:** Validate calendar dates and nonempty valid candidate sets before constructing DatesAnswer; share validation with parsing.
- **Required verification:** Negative constructor tests for invalid calendars and empty patterns, plus valid leap-day and ordinary pattern acceptance.

#### AUD-009-API002 - Low - EncodedBackup.of accepts sparse index arrays

- **Category:** API.
- **Status:** fixed.
- **Release blocking:** false; bounded constructor-contract failure without demonstrated incorrect recovered wallet.
- **Affected files and builds:** `src/core/encoded-backup.ts:121`; exported Node/browser-host API
- **Reproduction:** EncodedBackup.of(new Array<number>(12), 'indexes', 'direct') succeeds; unchecked seedshift-legacy has the same validation shape.
- **Expected behavior:** Every index is a present integer within the BIP39 index range before the object is constructed.
- **Observed behavior:** Array.some skips holes; constructor spread materializes undefined elements. Decoding later rejects the invalid indexes.
- **Impact and limits:** Malformed native/browser host input produces an invalid public object. CLI read creates dense arrays; no accepted incorrect mnemonic or secrecy compromise is demonstrated.
- **Evidence:** core-invariants.log: missing expected exception for new Array<number>(12).
- **Recommended fix:** Validate every indexed position including holes, using the explicit density checks already present in candidate handling.
- **Required verification:** Reject sparse/partially sparse arrays, undefined and out-of-range entries; retain dense valid round-trips in all supported modes.
