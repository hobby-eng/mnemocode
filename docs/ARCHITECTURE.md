# Source layout

MnemoCode is an offline command-line program and a TypeScript library. The library holds the rules; the CLI asks, shows and saves. Renderers do no mnemonic or share arithmetic. The package entry points `src/index.ts`, `src/cards.ts` and `src/sskr/index.ts` gather the library for Node.js programs, and each part of it also has an entry of its own for other hosts ([Modules for other hosts](#modules-for-other-hosts)).

`src/version.ts` holds the version. The toolchain check requires it to match `package.json`.

## Transformation layer

`src/core.ts` re-exports the modules in `src/core/`:

| Module                    | Responsibility                                                      |
| ------------------------- | ------------------------------------------------------------------- |
| `core/types.ts`           | Public result types, the forms of codes and the masking modes       |
| `core/bip39-sizes.ts`     | The sizes of a BIP39 phrase: word counts, entropy and checksum bits |
| `core/english-words.ts`   | The English word list alone: tokens, phrases and the checksum       |
| `core/words.ts`           | Word lists, index maps and mnemonic validation                      |
| `core/bits.ts`            | Bit/byte conversion and modular arithmetic                          |
| `core/dates.ts`           | Calendar validation, ordering, shift schedule and recovery patterns |
| `core/colors.ts`          | BIP39Colors decimal packing and Private Use Unicode transport       |
| `core/representations.ts` | Representation parsing, detection and formatting                    |
| `core/seedshift.ts`       | Direct, checksum-valid and legacy transformations and inverses      |

Core modules do not import CLI input, PDF renderers, image tools or the share runtime. The final entropy chunk uses [its own modulus](../README.md#how-checksum-valid-seedshift-works); comments beside both directions of the transformation explain it. Legacy last-word recovery searches widely so that old records stay readable.

`record.ts` parses the versioned MNC1 record. `core/wallet-evidence.ts` checks recovery evidence and derivation paths with the PBKDF2 that its host passes, and `bitcoin-evidence.ts` passes Node's. The other modules in `core/` are parts of their own, described in [Modules for other hosts](#modules-for-other-hosts).

## CLI

`mnemocode.ts` starts the menu (`cli/menu.ts`) when there is no command and a terminal, and otherwise `cli/command-line.ts`, which dispatches commands and rejects unsupported flags. The menu only builds a command line from its questions and runs it through the same dispatcher. `cli/input.ts` owns interactive and file input. `arguments.ts` and the option modules validate values.

`scripts/verify-terminal-input.py` drives the menu and the prompts for secrets in a real pseudo-terminal: a Unix one on Linux and macOS, a Windows pseudo-console through pywinpty. Its session and screen are `scripts/terminal_session.py`, the public answers it types are `scripts/terminal_answers.py`, and its checks are `scripts/terminal_menu_checks.py` and `scripts/terminal_secret_checks.py`.

`output-paths.ts` checks destinations before any secret is requested. This check is not a lock: the writers still enforce exclusive creation.

`encode-command.ts` coordinates one transformation, `encode-report.ts` formats its terminal result and `encode-export.ts` saves it. Recovery, previews and the table each have their own command module. Terminal colour styling is in `terminal.ts`.

## Cards and files

`export/templates.ts` is the template registry. Each card family has a renderer, a layout module and an artwork module. Layout dimensions are millimetres. Text helpers convert the top-of-line-box convention to PDF coordinates. Typography profiles and named geometry constants stay near the drawing code.

`card-identities.ts` selects the employer, role and name. `card-copy.ts` separately selects the studio and the sheet text. `export-details.ts` (`ExportDetails`) owns both for one export: it settles them once where the export starts, from the export's settings or the options of a command, and every page, output format and share prints them. `card-session.ts` remembers these choices for a host that exports several times in one session.

`world-map.ts` holds the projection of the world map behind a collection sheet; `world-map-data.ts` is generated from public-domain Natural Earth data by `scripts/build-world-map.mjs`.

`card-qr.ts` draws vector modules and enforces the quiet zone and the module size. The payload is validated before drawing. An individual card never receives the payload of the whole collection or of a whole share.

The renderers contain no Node.js code. They get bundled files, random choices, PNG coding and QR matrices from the interface in `export/platform.ts`; `export/platform-node.ts` supplies them for Node.js. A host builds one `CardRenderer` (`export/card-renderer.ts`) with them and passes it to every render: `renderCards` and `renderIndividualCards` from `export/render.ts`, `ShareCardSet`, `CardPreview`, `renderHeirSheet` and the self-tests of cards. The renderer keeps the artwork that it prepared with its platform; no module keeps a platform of its own. `src/cards.ts` is the entry point for another host, such as a browser page.

`ShareCardSet.forIndividualCards({ pageSize, orientation })` turns an existing collection into separate cards without rendering or drawing new random values. It retains every share's codes, decorative colors, first decoy, identity and references; the original sheet stays unchanged. The size defaults to `business`, only the explicitly requested orientation applies, and whole-share QR cards and sheet-only designs are refused.

`heir-sheet-text.ts` writes the words of the sheet for heirs, along the route through the host's own program that the host passes, and `heir-sheet.ts` lays out both sides in A5 or A6. `sskr-render.ts` renders the cards of shares. `backup-cards.ts` builds the content of the cards of an encoded backup (`backupCardContent`), which every save, Encode's dry run and the sample cards draw. `template-catalog.ts` lists the designs by id, kind and style and reads a design named by its id or its number (`resolveTemplateId`), without the renderers that `templates.ts` adds; the employer on business cards follows the style (`sectorForStyle`). A set of cards is planned before it is drawn: `card-palette.ts` gives the cards that print codes their colors, `card-decoys.ts` adds the decoys after a backup's codes and keeps the ones a plan takes, and `card-plan.ts` keeps exactly one decoy for separate cards. For sheets it plans their number and the orientation through `planCollectionSheet` in `collection-layout.ts`, which lays out the sheets that `collection-sheet.ts` draws, with the sheet shape of each design (`CardTemplate.sheetShape`). `business-tint.ts` holds the tint of the business artwork that the recoloring, the ink of the curves design and the palette share. `pdf.ts`, `individual-cards.ts` and `sskr-cards.ts` organize documents and destinations. `image-export.ts` converts those same PDFs to images with local Poppler. `private-file.ts` publishes file exports as new private files through a staging directory on the same filesystem, never over an existing name. Artwork derived from a user's references is cached only for the current document; shared caches contain fixed bundled artwork.

## Modules for other hosts

`core/byte-array.ts` admits attached byte arrays using their intrinsic storage, without trusting a prototype or an own length getter. The candidate list and checked SSKR bridge share it. `export/file-name.ts` owns safe output-name validation for both filesystem exports and browser downloads. Rendered individual-card names are checked before drawing.

The library is built from parts that another host, such as the Wallet Deriver of the multi-chain wallet tools, takes one at a time: a program that only searches dates takes the date search and the few modules it imports, nothing about shares, cards or terminals ([Roadmap](ROADMAP.md)). Each part is one entry module, with a class wherever the part has data to keep, such as a share set or a search, and each is exported on its own under its path in `src/`, without the extension: `import { DateSearch } from "mnemocode/core/date-search"`. A part contains no Node.js code and imports only a few pure JavaScript packages. What only the host has comes in as a small parameter or interface: the share parts take the host's `SharePlatform` with each call or object that needs it, and use no other. The card parts take the host's `CardRenderer`, built with its `RenderPlatform`, and each drawing function asks only for the services it uses; `card-copy.ts` takes its random choice as a parameter. The header comment of each entry says what it does, what it needs from the host and what it does not do. The functions that callers already use stay: the transformations in `mnemocode`, the shares in `mnemocode/sskr`, and the older functions of a part beside its class, such as `planJointRepair`, which takes the host's platform as `JointRepair` does. The parts also compile with the two stricter flags that a host may use for the files it takes, `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess`, as the multi-chain wallet tools do: `pnpm check` compiles the whole program and its tests with them (`tsconfig.json`).

`mnemocode/core/word-table` exposes `WordTable`: lookup by a word, number or Unicode code,
numbered dictionary text, and the canonical mapping. It imports no Node.js, cards or shares.
`mnemocode/core/encoded-form` exposes `EncodedForm` directly: callers ask the form for its card
kind, color layout and masking rule. The older functions in `core/words` and `core/backup-options`
remain compatibility adapters; internal callers use the owners.

Coin families and their self-tests also have independent package entries under
`mnemocode/core/coins/`: `bitcoin-like`, `bitcoin-cash`, `dash`, `ethereum`, `evm`, `cosmos`, `xrp`
and their `-self-test` modules. `core/coins/coin` exposes `CoinList` and the common address contract;
`core/coins/base58` exposes `Base58Coin` for host configurations. A host composes its list from the
families it needs; `core/coins` remains the composition of all supported families. Coin descriptions
and Base58 version records are owned snapshots. The identity and path properties are getter-only.

SSKR host capabilities are narrow: `ShareCombiner` restores complete shares,
`ShareRepairPlatform` adds HMAC-SHA256, and `ShareSplitPlatform` adds creation with a restore
check. `SharePlatform` composes them all. A search run can supply `now`, a monotonic clock in
milliseconds, alongside its signal and event-loop turn; omitted clocks retain `performance.now`.
Timing methods accept the same optional clock, so tests need not replace global time.

Each feature keeps its checks in a module beside it named with `-self-test`, a `SelfTestFeature` (`core/self-test-check.ts`): quick known answers for `core()` and a row of the full self-test. The library's are composed by `core/self-test.ts`, a host adds the rest, so a build without wallet evidence, coins or cards carries none of their checks or vector text. Each coin family has its own self-test beside it in `core/coins/` (such as `dash-self-test.ts`), which `core/coins-self-test.ts` composes for a host of every coin; a host of one family takes that family's alone, and `test/one-coin-builds.test.ts` checks that the modules of Dash carry no other coin's words.

The parts use each other in one direction only, from features to the services and primitives below them, never back. Each uses exactly these parts (test/portable-modules.test.ts checks this list against its own):

- `sskr/share-platform` uses no other part.
- `export/platform` uses no other part.
- `export/card-renderer` uses `export/platform`, `export/card-copy` and `sskr/transport`.
- `core/master-fingerprint` uses no other part.
- `core/coins` uses no other part.
- `core/coin-address-evidence` uses `core/master-fingerprint`.
- `core/wallet-evidence` uses `core/master-fingerprint` and `core/coin-address-evidence`.
- `core/masking` uses no other part.

Below the parts are modules that need nothing from the host and that hosts compile as they are: in `core/` the words, bits, calendar, colors, representations, Seedshift, `date-recovery.ts`, and the small helpers that the parts share (`wallet-check.ts`, the shape of a host's wallet check; `search-turns.ts`, the turns of a long search; `places.ts`, how a message names places; `white-space.ts`, the trimming of a typed answer; `address-scan.ts`, the addresses compared from an index on; `bip32-limits.ts`, the bounds of BIP32 indexes; `typed-number.ts`, a whole number as a person types it; `word-hints.ts`, the hints below a word being typed and the completion with Tab); `record.ts`; in `core/coins/` the forms of addresses that the families share (`address-types.ts`, `base58-check.ts`, `bech32.ts`, `other-forms.ts`) and those of some families only (`taproot.ts` for Bitcoin's, `keccak-account.ts` for the Ethereum-style accounts of the EVM coins and Injective); in `export/` the codes a card prints (`card-codes.ts`), the content a card's QR code must hold (`card-content.ts`), the colors of codes (`card-palette.ts`), the decoys (`card-decoys.ts`), the tint of the business artwork (`business-tint.ts`), the documents with the bundled font and their joining (`pdf-documents.ts`) and the backdrops of sheets (`study-backdrops.ts`); and in `sskr/` the checksum, the arithmetic, the units of each share form (`share-units.ts`), the layout of shares in colors and words (`mixed-layout.ts`) and the repair of one share (`repair.ts`, with `repair-models.ts` and `repair-units.ts`). `core.ts` gathers the transformations for the `mnemocode` entry; no part reaches it, each imports the `core/` modules it needs. A part never imports `mnemocode`, `mnemocode/cards` or `mnemocode/sskr`, which stay for existing callers: `mnemocode` and `mnemocode/sskr` carry the Node.js platforms, and `mnemocode/cards` gathers the host-neutral card modules. `test/portable-modules.test.ts` imports each part alone and fails when it reaches Node.js code, a package not allowed for it, a part it does not name, the CLI, `core.ts` or one of those entries.

The bundled SSKR bridge returns `Error` objects with stable `sskr.engine.*` codes for its Rust-owned refusals; callers must not use raw thrown strings or parse messages to identify a failure. `CheckedSskrBridge` validates attached byte arrays before the generated glue copies a secret, owns and wipes the temporary input copies, and leaves borrowed caller buffers unchanged. A host converting a member threshold/count to bytes must first call `CheckedSskrBridge.groupSpecifications(threshold, count)` so values such as 258 cannot silently become 2. Source, generated glue/WASM and `integrity.json` are synchronized together.

Render methods transfer ownership of fresh document buffers to their caller; failure wipes earlier owned results. Export methods wipe them after saving or refusing. A caller that uses a combined share document generator must close it when abandoning iteration, allowing the generator to wipe the yielded page. Joining documents borrows its inputs and does not erase them. Individual output filenames use the host-neutral `ExportFileName.checked()` policy for both filesystem paths and browser downloads.

`ShareCardSet` and the CLI's `EncodeCardExport` retain colors, labels and QR payloads in `CardValues`, which owns their UTF-16 code units in mutable bytes. Their creating callers keep the plan live through every awaited render and save, then call `wipe()` or leave its `using` scope. Wiping closes the owner immediately and refuses later secret reads with `core.secret-value.wiped`; a `ShareCardSet` render that finishes afterwards wipes its fresh document bytes and refuses publication. Public layout and share-reference metadata may remain. `forIndividualCards()` creates an independently owned plan; ending either plan leaves the other live. Encode borrows its backup without retaining the whole encoding outcome, shares the first pending planning operation, and caches only a completed live plan. A failed plan can be retried. Already returned job views and third-party decoded copies cannot be recalled or guaranteed erased.

`EncodedBackup`, `ReEncoding`, `Share` and `PassphraseProtection` retain their secret values in owned byte storage. Their owning caller uses `using` or `finally` to call `wipe()` after all asynchronous uses have settled; `[Symbol.dispose]()` calls `wipe()`. Further secret reads are refused with `core.secret-value.wiped`. `ReEncoding` snapshots its input backup, so disposing either owner leaves the other independent. Returned compatibility strings and frozen arrays are temporary caller-owned views: disposing the owner cannot recall those views or erase copies made by the runtime.

`DatesAnswer` keeps complete dates, numeric pattern lists, arbitrary pattern keys and typed positions in owned bytes. Pattern keys preserve every UTF-16 code unit, including lone surrogates; UTF-8 passphrase storage keeps its separate encoding contract. Its `copy()` preserves those values with an independent lifetime. `DateSearch` owns its indexes and a copy of its input answer: disposing either input or search leaves the other independent. An incomplete answer passed to `MissingCodesSearch.byWallet`, or an answer passed to `ShareUnmasking`, is borrowed until the returned way or unmasking has finished all its work; its creating caller disposes it afterwards.

`CandidateListWriter` owns its BIP39 passphrase and borrows its `ListProtection`; disposing the writer leaves that protection alone. The built-in protections implement `OwnedListProtection`, whose creating caller disposes it. A protection transfers fresh result bytes, or the input buffer itself, to the writer, which copies and wipes them. The CLI's `CandidatesFile` owns both its writer and its built-in protection. Saving entropies transfers them to that call, which wipes them on success, refusal and cancellation, including a refusal before writing starts.

The Node.js hosts sit beside the parts: `bitcoin-evidence.ts` builds a `WalletEvidenceCheck` with node:crypto's PBKDF2, `sskr/share-platform-node.ts` supplies the share platform and `export/platform-node.ts` the render platform and the card renderer built with it (`nodeCardRenderer`). A browser page supplies its own, with these limits:

- WebCrypto's PBKDF2 answers asynchronously: a page passes it to `WalletEvidenceCheck` and checks with `matchAsync`, which the date search, the word search and the restore of masked shares take as their wallet check. WebCrypto's HMAC is asynchronous too, while the share repair calls it for every combination, so a page passes the `hmac` of `@noble/hashes` in its share platform. A long search runs in a worker.
- X25519 is in WebCrypto only on a secure page, served over https or from localhost. Elsewhere a list for the Scanner's key is refused with one line, and a list under a passphrase still works.
- The command line makes images of pages with Poppler's `pdftocairo`, which a page lacks: the parts give PDF bytes, `export/card-drawing.ts` (`CardPdfReader`) reads them back as drawing steps, and the page paints those on its canvas. The reader accepts only the PDF commands the renderers write, and `test/card-drawing.test.ts` reads the cards of every renderer through it. The command line also reads QR codes from PNG images itself; a page reads them its own way.
- A reusable `CardPdfReader` owns its decoded image and font buffers. `pages()` borrows image bytes until `wipe()` or disposal; `takePages()` transfers the images and ends the reader. The one-shot `readCardPages()` does the same transfer automatically. A host wipes transferred image `data` and `alpha` after painting, once per shared image. Wiping a reader does not change the caller's input PDF; immutable drawing views and dependency/runtime copies cannot be guaranteed erased.
- Files, the private screen, Ctrl+C and the [protection while it runs](../README.md#protection-while-it-runs), with its warnings about swap and cloud folders, belong to the command line.
- A host stops a long search, the assessment of marked shares among them, with the `AbortSignal` it passes. A stop is no failure: the search ends at its next turn and gives what it found before the stop, marked as stopped (`stopped: true`, the kind `"stopped"` or the verdict `"stopped"`), and nothing found after it.
- The parts wipe the byte arrays they own once they are done with them, also when they refuse or are stopped. A plan of a share repair keeps the arrays it searches with for as long as the host keeps the plan. Neither host can wipe a JavaScript string.

For repeated wallet comparisons, `WalletEvidenceCheck.prepare(evidence, passphrase)` returns an independently owned comparison with `match()` and `matchAsync()`. It retains passphrase bytes and parsed evidence, including a WIF key, until its caller disposes it. A comparison that settles after disposal is refused. The service itself remains reusable; one-off `match()` and `matchAsync()` create and dispose a temporary comparison. Node's `walletCheckOf()` remains callable and also provides `wipe()` and `[Symbol.dispose]()`; keep it live through the awaited search, then dispose it. A search borrows that callback and never disposes it for its host.

Refusals use `core/error-catalog.ts`: each module owns its stable code list and default English messages, while one shared implementation creates the error. The code is immutable; the existing message, native `TypeError` or `RangeError` identity, and `cause` are preserved. `CodedFailure` is exported as a type from the core API. A host may display the default message or choose its own wording from the code; changing wording does not change a code. A refusal supplied by an existing shared rule uses `suppliedMessage`, without copying the rule's formatter. Existing specialized error classes keep their codes. Operational failures thrown by dependencies or host callbacks still pass through; they are not reclassified as cancellation.

Terminal questions return `CANCELLED` for Ctrl+C or ended input, rather than throwing. Yes/no answers are `"yes"` and `"no"`; waiting for a key gives `"enter"`, `"escape"` or `CANCELLED`. The entry point prints the cancellation line and sets exit code 130 once. Library searches use their documented stopped result, and a host must keep it separate from a completed search with no matches. If a host cancels after the final share-assessment callback, `ShareRestore.read` wipes the plan and returns the stopped result before timing or handing it out.

`BackupReading` owns its retained payload bytes until `wipe()` or `[Symbol.dispose]()`. Hosts keep it live through asynchronous mode/format questions and dispose it after creating the child backup or marked-code search, including refusal and cancellation paths. Those children own independent copies; ending the reading does not dispose them. Record mode/format metadata remains available after disposal, while payload-dependent operations refuse. Decoded strings and caller-owned inputs cannot be recalled or erased by this owner.

`MissingCodes` likewise owns its retained candidate-place bytes and exposes `wipe()` / `[Symbol.dispose]()`. It closes active candidate iterators when disposed and refuses new secret reads; `withMode()` makes an independent owner. Keep it live through an asynchronous run. Successful and stopped runs transfer their kept `EncodedBackup` results to the caller, which disposes them; a failed run wipes those results itself. Candidate arrays already returned to a caller are independent views and cannot be recalled. Decode retains marked codes through any later result redisplay and ends them on retry or exit.

The prepared ways of `MissingCodesSearch` are disposable owners too: keep each way live through its awaited plan and run, then call `wipe()` or leave its `using` scope. Each way owns a byte snapshot of complete dates, borrows marked codes and any incomplete date answer, and releases its references to host callbacks when disposed. Ending a way never disposes those borrowed inputs. Later planning, running or publication after an awaited host callback is refused with `core.missing-codes-search.way-wiped`. A run disposes all temporary backups unless it transfers the sole matching backup to its caller; that backup and returned date views survive the way's disposal.

`ShareInput` owns the code units of the shares it retains, including input that has not yet passed transport validation. Replacing that input ends its previous storage. Keep the input owner live through awaited restoration; disposal also prevents a later host result from being published. `ShareSet` owns independent copies of the restored phrase and repaired shares. `ShareExport` owns the shares to be written, and `inForm()` creates an independent export. Their creating callers dispose them after their asynchronous uses. Borrowed input objects and already-returned plain views remain independent; wiping an owner cannot recall those views.

Each `MarkedReading.of()` result is independently owned. Its `space()` solves into a `ReadingSpace` that owns a separate reading copy and exact affine coordinates; dispose both owners when their work ends. The space's `reading` getter borrows its child, so copy that reading to keep it beyond the space's lifetime. `withSpace()` scopes a temporary space for synchronous use. A joint repair plan owns its selected spaces and branches until `wipe()` or disposal; ending it refuses later searches and late publication with `sskr.joint-repair.plan-wiped`. Ordinary signal cancellation still returns the documented stopped outcome. `ShareVariantsError` carries only candidate count and changed places; candidate share records travel in the ordinary repair result.

## Single executable

`bundled-files.ts` reads every file that ships with the program, such as card artwork, the SSKR engine and the public vectors, by its path from the package root: next to the code when MnemoCode runs from a checkout or an installed package, and from the embedded assets inside the single executable.

`scripts/build-executable.mjs` bundles the CLI with esbuild into one CommonJS file and builds a Node.js single executable from it, with the bundled files as assets. It also writes the license notices of everything the executable contains (`scripts/executable-notices.mjs`) and the SHA-256 lines of both files. `scripts/verify-executable.mjs` runs the executable of this system from an empty folder. `.github/workflows/executable.yml` builds and checks it on Linux, Windows and macOS, and on a version tag puts the files and `SHA256SUMS` into a draft release after the complete CI has passed; the maintainer signs and publishes it ([RELEASING.md](RELEASING.md)).

## Maintenance checks

Format the project's TypeScript and JavaScript with the checked-in Prettier configuration, then run `corepack pnpm check` and `corepack pnpm build`. Generated files and the SSKR bridge are excluded from formatting.

For layout refactoring, `scripts/business-goldens.mjs` creates fixed public fixtures with the build of a given checkout and `scripts/compare-business-goldens.py` compares every PDF of two such folders at 144 dpi. The fixtures, the loading of a build and the reading of a card's QR code are shared with `scripts/check-card-output.mjs` (`scripts/card-fixtures.mjs`). The comparison covers those fixtures, not every combination of design and input. Keep refactoring separate from intended design changes.

Formatting and compiler checks do not replace the full test run. Run the full suite and `mnemocode self-test` before a release.
