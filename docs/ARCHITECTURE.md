# Source layout

MnemoCode is an offline command-line program and a TypeScript library. The library holds the rules; the CLI asks, shows and saves. Renderers do no mnemonic or share arithmetic. The package entry points `src/index.ts`, `src/cards.ts` and `src/sskr/index.ts` gather the library for Node.js programs, and each part of it also has an entry of its own for other hosts ([Modules for other hosts](#modules-for-other-hosts)).

`src/version.ts` holds the version. The toolchain check requires it to match `package.json`.

## Transformation layer

`src/core.ts` re-exports the modules in `src/core/`:

| Module                    | Responsibility                                                      |
| ------------------------- | ------------------------------------------------------------------- |
| `core/types.ts`           | Public result types and supported word counts                       |
| `core/words.ts`           | Word lists, index maps and mnemonic validation                      |
| `core/bits.ts`            | Bit/byte conversion and modular arithmetic                          |
| `core/dates.ts`           | Calendar validation, ordering, shift schedule and recovery patterns |
| `core/colors.ts`          | BIP39Colors decimal packing and Private Use Unicode transport       |
| `core/representations.ts` | Representation parsing, detection and formatting                    |
| `core/seedshift.ts`       | Direct, checksum-valid and legacy transformations and inverses      |

Core modules do not import CLI input, PDF renderers, image tools or the share runtime. The final entropy chunk uses [its own modulus](../README.md#how-checksum-valid-seedshift-works); comments beside both directions of the transformation explain it. Legacy last-word recovery searches widely so that old records stay readable.

`record.ts` parses the versioned MNC1 record. `core/wallet-evidence.ts` checks recovery evidence and derivation paths with the PBKDF2 that its host passes, and `bitcoin-evidence.ts` passes Node's. The other modules in `core/` are parts of their own, described in [Modules for other hosts](#modules-for-other-hosts).

## Shamir shares (SSKR)

| Module                        | Responsibility                                                                         |
| ----------------------------- | -------------------------------------------------------------------------------------- |
| `sskr/share-platform.ts`      | The host's services for shares: HMAC-SHA256 and its SSKR library                       |
| `sskr/split.ts`               | Splits a phrase into the shares of one group and checks that they give it back         |
| `sskr/share-set.ts`           | Restores a set of shares, checks every share given against it, and the export rules    |
| `sskr/share-input.ts`         | Shares as typed: each read, copies used once, the set checked, the wrong share named   |
| `sskr/repair-report.ts`       | What a repair of marked shares tells, as lines of data with their texts                |
| `sskr/share-unmasking.ts`     | The seed phrases that restored sets give: unmasked with the dates, or searched         |
| `sskr/transport.ts`           | Bytewords, CBOR and ordered RGB records, with named constants for the byte rules       |
| `sskr/checksum.ts`            | Shared CRC32 and reversible layout mixing                                              |
| `sskr/repair.ts`              | Reads a share with marked elements, and solves one share from its own checks           |
| `sskr/joint-repair.ts`        | Solves marked shares of one set together; the digest search over what is open          |
| `sskr/gf2.ts`                 | Elimination over GF(2), with bit vectors in bigints                                    |
| `sskr/gf256.ts`               | GF(256) arithmetic and Lagrange coefficients, as bc-shamir uses them                   |
| `sskr/self-test.ts`           | Checks the published grouped vector                                                    |
| `sskr/runtime.ts`             | Verifies and loads the local WASM; supplies operating-system randomness                |
| `sskr/share-platform-node.ts` | The share platform for Node.js: node:crypto and the bundled WASM                       |
| `sskr/shares.ts`              | The functions of `mnemocode/sskr`: the self-test, then the modules above with Node.js  |
| `cli/sskr-command.ts`         | The share commands: their options, questions and output                                |
| `cli/share-repair.ts`         | Shares on the screen: typed again or left out, the repair report, the search question  |
| `export/sskr-render.ts`       | Renders existing shares as cards: the whole set, or each share in documents of its own |
| `export/sskr-cards.ts`        | Writes the cards of shares to files and folders, and their pages as images             |

`sskr-wasm` contains the Rust source of the share library, its Cargo lockfile, the generated JavaScript and WASM, and their notices. `pnpm build:sskr` builds the WASM from that source offline in the pinned container `Dockerfile.sskr`; `pnpm verify:sskr` builds it again and compares the result byte for byte. `sskr-wasm/integrity.json` pins the hashes of these files, so the formatter must not rewrite them. [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md) names the library versions and licenses.

## CLI

`mnemocode.ts` starts the menu (`cli/menu.ts`) when there is no command and a terminal, and otherwise `cli/command-line.ts`, which dispatches commands and rejects unsupported flags. The menu only builds a command line from its questions and runs it through the same dispatcher. `cli/input.ts` owns interactive and file input. `arguments.ts` and the option modules validate values.

| Module                   | Responsibility                                                                  |
| ------------------------ | ------------------------------------------------------------------------------- |
| `cli/terminal-input.ts`  | Raw terminal keys and typed answers, the same on Linux, macOS and Windows       |
| `cli/terminal-choice.ts` | Lists chosen with the arrow keys, typed answers and the pause for Enter         |
| `cli/private-screen.ts`  | The alternate screen for typed secrets and their results, cleared after Enter   |
| `cli/protection.ts`      | No core dumps, the permission model, and what a command gives up before it runs |
| `cli/swap-check.ts`      | Whether swap is encrypted (Linux)                                               |
| `cli/cloud-folders.ts`   | Whether an output path lies in a cloud-synchronised folder                      |
| `cli/menu.ts`            | The entries, their questions and the command line each answer builds            |
| `cli/ask.ts`             | Questions asked again until their answer can be used                            |
| `cli/save-retry.ts`      | A save that fails on the private screen: try again, another name, or skip       |
| `cli/menu-entries.ts`    | The entries of the start menu, by which every message and the sheet name them   |
| `cli/date-search.ts`     | The encoded seed phrase, its mode and its dates on the screen, and the search   |
| `cli/backup-check.ts`    | The questions of the optional check of a backup typed again after Encode        |
| `cli/heir-sheet.ts`      | The route through the menu that the sheet for heirs prints (`--heir-sheet`)     |

`scripts/verify-terminal-input.py` drives the menu and the prompts for secrets in a real pseudo-terminal: a Unix one on Linux and macOS, a Windows pseudo-console through pywinpty.

`output-paths.ts` checks destinations before any secret is requested. This check is not a lock: the writers still enforce exclusive creation or private atomic replacement.

`encode-command.ts` coordinates one transformation, `encode-report.ts` formats its terminal result and `encode-export.ts` saves it. Recovery, previews and the table each have their own command module. Terminal colour styling is in `terminal.ts`.

## Cards and files

`export/templates.ts` is the template registry. Each card family has a renderer, a layout module and an artwork module. Layout dimensions are millimetres. Text helpers convert the top-of-line-box convention to PDF coordinates. Typography profiles and named geometry constants stay near the drawing code.

`card-session.ts` remembers these choices for a host that exports several times in one session. `card-identities.ts` selects the employer, role and name. `card-copy.ts` separately selects the studio and the sheet text. Both are resolved once at the export boundary and passed to every page and output format.

`world-map.ts` holds the projection of the world map behind a collection sheet; `world-map-data.ts` is generated from public-domain Natural Earth data by `scripts/build-world-map.mjs`.

`card-qr.ts` draws vector modules and enforces the quiet zone and the module size. The payload is validated before drawing. An individual card never receives the payload of the whole collection or of a whole share.

The renderers contain no Node.js code. They get bundled files, random choices, PNG coding and QR matrices from the interface in `export/platform.ts`; `export/platform-node.ts` supplies them for Node.js. `src/cards.ts` is the entry point for another host, such as a browser page, which calls `configureRenderPlatform` and then uses `renderCards` or `renderIndividualCards` from `export/render.ts`.

`heir-sheet-text.ts` writes the words of the sheet for heirs, along the route through the host's own program that the host passes, and `heir-sheet.ts` lays out both sides in A5 or A6. `sskr-render.ts` renders the cards of shares. `pdf.ts`, `individual-cards.ts` and `sskr-cards.ts` organize documents and destinations. `image-export.ts` converts those same PDFs to images with local Poppler. `private-file.ts` replaces file exports through a private staging directory on the same filesystem. Artwork derived from a user's references is cached only for the current document; shared caches contain fixed bundled artwork.

## Modules for other hosts

The library is built from parts that another host, such as the Wallet Deriver of the multi-chain wallet tools, takes one at a time: a program that only searches dates takes the date search and the few modules it imports, nothing about shares, cards or terminals ([Roadmap](ROADMAP.md)). Each part is one entry module, with a class wherever the part has data to keep, such as a share set or a search, and each is exported on its own under its path in `src/`, without the extension: `import { DateSearch } from "mnemocode/core/date-search"`. A part contains no Node.js code and imports only a few pure JavaScript packages. What only the host has comes in as a small parameter or interface: the share parts take the host's `SharePlatform` with each call or object that needs it, and use no other. Only the card renderers read a service configured once: the render platform, which every drawing function needs deep inside, from `configureRenderPlatform`, as `mnemocode/cards` has always done; `card-copy.ts` also takes its random choice as a parameter. The header comment of each entry says what it does, what it needs from the host and what it does not do. The functions that callers already use stay: the transformations in `mnemocode`, the shares in `mnemocode/sskr`, and the older functions of a part beside its class, such as `planJointRepair`, which without a platform of its own uses the configured one. The parts also compile with the two stricter flags that a host may use for the files it takes, `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess`, as the multi-chain wallet tools do: `pnpm check` compiles `src/core/`, `src/sskr/` and `src/export/` with them (`tsconfig.strict-consumers.json`).

Each feature keeps its checks in a module beside it named with `-self-test`, a `SelfTestFeature` (`core/self-test-check.ts`): quick known answers for `core()` and a row of the full self-test. The library's are composed by `core/self-test.ts`, a host adds the rest, so a build without wallet evidence, coins or cards carries none of their checks or vector text. Each coin family has its own self-test beside it in `core/coins/` (such as `dash-self-test.ts`), which `core/coins-self-test.ts` composes for a host of every coin; a host of one family takes that family's alone, and `test/one-coin-builds.test.ts` checks that the modules of Dash carry no other coin's words.

The parts use each other in one direction only, from features to the services and primitives below them, never back:

- `encoded-backup` and `date-search` use `masking`; `missing-codes` uses `candidates`, `encoded-backup` and `masking`; `backup-reading` uses `encoded-backup`, `masking`, `missing-codes` and the share forms (`transport`).
- `joint-repair` and `split` use the share platform and the share forms; `repair-report` uses `joint-repair`; `share-set` uses `joint-repair` and `repair-report`; `share-input` uses `share-set`; `share-unmasking` uses `date-search`, `encoded-backup` and `joint-repair`.
- `backup-options` uses `masking` and `split`; `backup-check` uses `date-search`, `encoded-backup`, `share-set` and `share-input`.
- `card-copy` and `heir-sheet` use the render platform; `sskr-render` uses `card-copy` and the share forms, and `heir-sheet-text` uses `heir-sheet`.
- `coin-address-evidence` uses `master-fingerprint`; `wallet-evidence` uses `coins`, `coin-address-evidence` and `master-fingerprint`; `coins`, `candidates`, `candidate-list` and `candidate-encryption` use no other part.

Below the parts are modules that need nothing from the host and that hosts compile as they are: in `core/` the words, bits, calendar, colors, representations, Seedshift, `date-recovery.ts`, and the small helpers that the parts share (`wallet-check.ts`, the shape of a host's wallet check; `search-turns.ts`, the turns of a long search; `places.ts`, how a message names places); `record.ts`; and in `sskr/` the checksum, the arithmetic and the repair of one share (`repair.ts`). `core.ts` gathers the transformations for the `mnemocode` entry; no part reaches it, each imports the `core/` modules it needs. A part never imports `mnemocode`, `mnemocode/cards` or `mnemocode/sskr`, which stay for existing callers and set up Node.js. `test/portable-modules.test.ts` imports each part alone and fails when it reaches Node.js code, a package not allowed for it, a part it does not name, the CLI, `core.ts` or one of those entries.

The Node.js hosts sit beside the parts: `bitcoin-evidence.ts` builds a `WalletEvidenceCheck` with node:crypto's PBKDF2, `sskr/share-platform-node.ts` supplies the share platform and `export/platform-node.ts` the render platform. A browser page supplies its own, with these limits:

- WebCrypto's PBKDF2 answers asynchronously: a page passes it to `WalletEvidenceCheck` and checks with `matchAsync`, which the date search, the word search and the restore of masked shares take as their wallet check. WebCrypto's HMAC is asynchronous too, while the share repair calls it for every combination, so a page passes the `hmac` of `@noble/hashes` in its share platform. A long search runs in a worker.
- X25519 is in WebCrypto only on a secure page, served over https or from localhost. Elsewhere a list for the Scanner's key is refused with one line, and a list under a passphrase still works.
- Images of pages need Poppler's `pdftocairo`, which a page lacks: the parts give PDF bytes. The command line also reads QR codes from PNG images itself; a page reads them its own way.
- Files, the private screen, Ctrl+C and the [protection while it runs](../README.md#protection-while-it-runs), with its warnings about swap and cloud folders, belong to the command line.
- The parts wipe the byte arrays they own. Neither host can wipe a JavaScript string.

## Single executable

`bundled-files.ts` reads every file that ships with the program, such as card artwork, the SSKR engine and the public vectors, by its path from the package root: next to the code when MnemoCode runs from a checkout or an installed package, and from the embedded assets inside the single executable.

`scripts/build-executable.mjs` bundles the CLI with esbuild into one CommonJS file and builds a Node.js single executable from it, with the bundled files as assets. It also writes the license notices of everything the executable contains (`scripts/executable-notices.mjs`) and the SHA-256 lines of both files. `scripts/verify-executable.mjs` runs the executable of this system from an empty folder. `.github/workflows/executable.yml` builds and checks it on Linux, Windows and macOS, and on a version tag publishes the files after the complete CI has passed.

## Maintenance checks

Format the project's TypeScript and JavaScript with the checked-in Prettier configuration, then run `corepack pnpm check` and `corepack pnpm build`. Generated files and the SSKR bridge are excluded from formatting.

For layout refactoring, `scripts/business-goldens.mjs` creates fixed public fixtures and `scripts/compare-business-goldens.py` compares their pages at 144 dpi. The comparison covers those fixtures, not every combination of design and input. Keep refactoring separate from intended design changes.

Formatting and compiler checks do not replace the full test run. Run the full suite and `mnemocode self-test` before a release.
