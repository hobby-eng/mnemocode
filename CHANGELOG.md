# Changelog

## 0.1.0 (unreleased)

First release of MnemoCode. The last two sections, "Toolchain and dependencies" and "Development", are for those who build or change the program.

### Distribution

- Each release has one executable file for Linux, Windows and macOS, with Node.js, the card artwork and the SSKR engine built in; `pnpm build:executable` builds it for the current computer.
- Each executable comes with a file of license notices for Node.js and every library it contains.
- The license notices hold the license texts of every crate that the SSKR engine's WebAssembly links, written from the crates' own sources, including the MIT notices of libsecp256k1, ur and phf. The repository and the npm package carry the same texts in `sskr-wasm/LINKED_LICENSES.txt`.
- The twelve images of the card designs were made for MnemoCode with image generation and are distributed under MnemoCode's MIT license. `assets/images/NOTICE` lists each image with its SHA-256; the license notices of the executables and `THIRD_PARTY_NOTICES.md` carry it.
- A release draft is made only after the complete CI has passed.
- GitHub signs the build provenance of every release file: `gh attestation verify` shows that a download was built from this repository by its release workflow.
- The `SHA256SUMS` of every release is signed with the maintainer's OpenPGP key, fingerprint `28FC51B1DB80DF2101128CB30EDD4814591DD095`, which GitHub also shows at https://github.com/hobby-eng.gpg. A tag creates a draft release, which the maintainer checks and signs on their own computer with `scripts/sign-release.mjs` before publishing it with `SHA256SUMS.asc` and `RELEASE-SIGNING-KEY.asc`; [Releasing](docs/RELEASING.md) describes the steps.
- The npm package includes the release notes and the guides for shares, cards and the source layout.
- The package and the executable carry no font for the Traditional Chinese BIP39 words: no card prints them.
- The README gives an overview. The [command-line reference](docs/CLI.md) holds the command examples and every option.

### Menu, help and terminal

- Started without a command in a terminal, for example by a double-click on the executable file, MnemoCode shows a menu. It asks step by step, with examples, and shows in grey the command that does the same before it runs it.
- The menu entries are 1 Encode, 2 Re-encode, 3 Decode, 4 Split, 5 Restore from Shamir shares, 6 Find a forgotten word, code, date digit or share code, 7 sample cards, 8 word lookup, 9 Run the self-test and 0 Show every command and option. Quit has no digit: Escape quits. The summary of `self-test` in the help also reads "Run the self-test".
- Encode in the menu lists the forms in the order of their `--format` numbers: 1 English words, 2 word numbers, 3 Unicode codes, 4 colors as text (Color Unicode) and 5 colors.
- Encode in the menu offers the usual sets of Shamir shares, such as 2 of 3 or 3 of 5, or any other up to 16 shares, and writes them in the form chosen; restoring them gives that form back.
- Entry 4 splits the seed phrase into standard SSKR shares, in Bytewords or as a `ur:sskr` code.
- The menu checks each of its own answers at once, such as a file name, a file dragged into the terminal, a fingerprint, an address or a share count, and asks again with one line that says why.
- A file dragged into the terminal is read by its path, also when the path holds an apostrophe.
- When a command stops unexpectedly, the menu offers to start it again with the same answers.
- After a failed self-test, the menu does not offer the entries that ask for a seed phrase or a share.
- Where the menu asks where a result or the shares go, All of these saves them to every place it offers at once: a record file, a QR code image and printable cards, or for shares a text file and cards, beside the screen.
- Enter repeats a word, number or Unicode lookup; Escape returns to the main menu.
- On a terminal, `table --word`, `--index` and `--unicode` show the row's index, English word and Unicode code as labelled facts under the heading "Word mapping". A file or a pipe gets plain lines.
- `mnemocode <command> --help` explains every option of a command with examples; `-h` gives a short summary.
- `mnemocode help version`, `mnemocode version --help`, `mnemocode help help` and `mnemocode help --help` show what those two commands do and how to call them.
- Every help page fits 80 columns, apart from the public test phrase, which cannot be split.
- Every help page ends with the same warning about recovery material.
- The layout follows where the output goes: a terminal gets headings, labelled facts, numbered phrases and marked notices, and a file, a pipe or `TERM=dumb` the plain lines of a script. `NO_COLOR` and `CLICOLOR=0` only take the colours away, and `CLICOLOR_FORCE` only adds colour.
- On the private screen, a result that does not fit with the question or prompt under it is shown whole by pages first, in its colours. This holds for a share set with its heading, notices and fingerprints, for the candidates of codes with `?` and for those of a decoded Original Seedshift backup. Its end then stays above the question, without the page keys, so that every line can be read on a small terminal too. Output sent to a file or a pipe keeps every line.
- In the pages, ↑ or PgUp and ↓ or PgDn turn the pages, Home and End go to the first and the last page, Enter or Escape ends them and Ctrl+C cancels. Home and End also work as a VT220 or tmux sends them. A key typed together with the one that ends the pages is dropped, so that a second Enter does not answer the question under them.
- Each question on the private screen has a screen of its own. The lines it needs stay above it until it is answered: the encoded fingerprint, so that a mistyped code shows before any date is typed, the reason of the Seedshift question, the form detected, re-encode's heading and confirmation of the new backup, and the Protection line.
- Encoded backups, Shamir shares and re-encode's confirmation stay on the private screen while the questions after them are asked. The screen is cleared only for another page or for the check of a written backup.
- A warning about unencrypted swap or a cloud folder stays on every step screen of the command, with its link. A cloud folder is warned of once, and only for a file that is saved: re-encode warns of the new backup's folder on the screen of its result.
- Every wallet fingerprint shown comes with one sentence: "They do not reveal the phrase." The menu shows its short label with that explanation in grey, also on narrow screens.
- While cards are checked and drawn on the private screen, a line names the step, such as "Checking that the cards can be printed…".
- The passphrase prompt of a candidate list says that it is the list's encryption passphrase, not the BIP39 passphrase.
- The passphrase of a candidate list is asked again, without a limit, until both entries agree.
- A path is shown without its control characters, so that a file name cannot move the cursor or erase a line.
- A typed line that is not valid UTF-8 is refused as such. Any other failure while the terminal is read, such as an unexpected error of the system, is reported as that failure, never taken for the end of the input.

### Formats

- Numbered representations are now consecutive: `colors-unicode` uses `--format 4` instead of `--format 6`.
- `colors-unicode` is written as four-digit codes rather than as the Private Use symbols themselves, which many programs cannot show. Decode reads the symbols too.
- Shares can also be written in Bytewords, the standard long form in words (`--share-format words`), as other SSKR tools write them, and, for MnemoCode only, as word numbers, Unicode codes or colors as Unicode codes (`indexes`, `unicode`, `colors-unicode`). A share file saved with `--output` holds the shares in the format shown, and `sskr-combine` shows the restored backup in the form of the shares.
- On a terminal, Unicode codes and colors as Unicode codes, which are written joined, are shown apart, separated by spaces, and then joined on one line, for copying: the encoded result, its shares and a backup restored from shares. A file or a pipe keeps the one joined line.
- Codes are read written apart or run together wherever they can be told apart: Unicode codes, colors, Color Unicode codes and shares in Bytewords, four letters a word, also with commas between the words or cut by a line break; the word hints follow them. Word numbers typed run together, which cannot be told apart, are refused with how to write them, and so is a `?` for one digit in codes run together.
- A date needs a four-digit year: `23-09-26` is refused.
- A record header whose version is written with leading zeros, such as `MNC01:`, is refused.

### Recovery

- Shares with unreadable elements can still be used: mark each with `?` at its place, on any of the shares, such as two words on each of three shares. MnemoCode repairs all of them together: the checksums, the data the shares have in common and every share beyond the threshold settle most marks without trying anything, and the SSKR secret digest decides the rest. Before any search it shows how many combinations are open, how long they take, and which element or how many more shares would settle them; a search longer than 12 hours is asked for first, or needs `--max-tries`. In colors and Unicode codes written apart, a `?` inside a code stands for one unreadable digit, such as `#B5?0??` or `4E?0`, and the digits read are used: those of a color as bits, those of a Unicode code by trying each word whose code fits. Every phrase that passes is listed with its fingerprint, never chosen, and a wallet check keeps the matching one. `sskr-combine` names every filled-in element, by share and place, so that the written copy can be corrected. Entry 6 of the menu and `sskr-export` give the repaired shares back whole, in their own form, without showing the phrase.
- One share below its threshold, with its first codes marked `?`, is repaired to the one share that fits, or Restore says that more shares are needed.
- A share in Color Unicode codes written apart takes a `?` for one digit of a code, such as `E1?A`, as colors and Unicode codes take it: its color is filled in from the colors whose codes fit the digits read. Color Unicode codes are shown apart code by code, four digits each. A share whose codes are run together with a `?` among the digits is refused with what such a `?` means: a whole code; to mark one digit, write the codes apart.
- When only as many shares as the threshold are given and they do not restore together, Restore says that they do not restore a secret and asks to check them and that all belong to one set. Only with more shares than needed can it name the one share that does not fit.
- A failure of the share engine is reported as a failure. Restore, the joint confirmation, the check of written shares and the split's own check never report it as wrong shares or as an empty result, and the check of written shares does not ask for the shares again after it.
- Shares whose groups each restore from one share, under a group threshold of 1, keep no SSKR digest. MnemoCode never writes such shares; for such shares made elsewhere, Restore says that the phrase is not checked, because a changed share would restore another phrase.
- The SSKR engine refuses a share whose group index is outside its group count. Its pinned libraries keep their algorithms and share formats, so valid shares keep their meaning.
- Fewer shares than the threshold cannot restore the phrase, but each share still shows the set identifier, the thresholds and the length of the phrase, as the help and the menu say.
- `recover-word` lists the words that can replace forgotten words and marks the candidates that match a known detail of the wallet. With `--legacy-valid-last-word` it lists the valid last words of a legacy phrase.
- `recover-word` finds several forgotten words, written as `?`, a beginning such as `ab*`, or a few words such as `rich|rice`, up to 16,777,216 combinations, and with `--missing-word` a word missing at an unknown place. Every candidate is checked offline against a wallet check when one is given.
- `recover-word`, `recover-date` and `sskr-combine` save their candidates with `--candidates-file` as a [candidate list](docs/CANDIDATES.md) for the Discovery Scanner of the multi-chain wallet tools: encrypted with age to the one-time key the Scanner shows, or with a passphrase; without encryption only with `--plaintext-candidates`. Entry 6 of the menu offers it. The search, the list and its encryption are host-neutral modules that the Wallet Deriver and the Scanner compile unchanged.
- Entry 6 of the menu also finds codes of an encoded seed phrase that cannot be read: typed with `?` at their places, as Decode reads them. Codes typed where the words of a seed phrase are asked for, as in `recover-word`, are pointed there.
- Codes with `?` in a number that no seed phrase has are refused before any of their places is read. Colors written as Unicode codes are counted as colors: "These are 7 colors; a seed phrase has 8 to 16."
- `re-encode` makes a backup again from one made before, with other dates, another mode, in another form, as cards or as Shamir shares, without the seed phrase being typed. It decodes the old backup as `decode` does and encodes its phrase as `encode` does, with `encode`'s options for the new backup and `--old-mode`, `--old-format` and `--old-dates-file` for the old one.
- With `--ask-secrets`, `re-encode` asks the old backup's dates right after its codes. It shows the phrase on the private screen and encodes it again only once it is confirmed, since its checksum proves nothing (MnemoCode Seedshift gives a valid phrase for every date): the person recognises it or its fingerprint (`--recognised`), or the wallet has an address or the fingerprint they name, of Bitcoin or another coin. A fingerprint has only 32 bits and is a filter, not proof: its match comes with that warning, and the phrase is accepted, not called confirmed; an address proves it. Only then is the new backup asked, with Encode's questions, unless options give it. A refused answer for the new backup is asked again.
- A backup of the Original Seedshift with a valid last word takes the remembered original final word privately or through `--last-word-file`. A last word given for a backup that gives one phrase is refused.
- `re-encode` writes the original seed phrase only to the private screen, never to standard output; its "New backup" heading goes there too.
- The master fingerprint and the other wallet checks compute the BIP39 seed with Node's own PBKDF2.
- Every wallet check also takes an address of another coin, the coins of mhfe on their standard paths: Bitcoin Cash, Cosmos, Dash (also Platform), Dogecoin, Ethereum and EVM networks, Ethereum Classic, Injective, Litecoin, Tron, XRP and Zcash (transparent). `--coin-address` with `--coin` gives it from the command line; in the menu, after Address, "Which coin is the address for?" lists every coin, Bitcoin first, then asks for its address. The library part `mnemocode/core/coins` reads and checks them for another host; `mnemocode/core/coin-address-evidence` checks an address of one coin given itself, so that a host of one coin, such as the Deriver's Dash edition, takes that coin's module alone.
- An address, a public key or a WIF is compared with the first 20 addresses of the wallet, from `--index` on, so that it need not be the first one: `--scan-gap N` sets how many, up to 1000, and the menu asks after the address, Enter for 20. The library takes the count as `addresses` in the evidence. An address of another coin given for the wrong one is refused as not that coin's, rather than as damaged.
- Messages name a wallet reference by its kind, such as "address" or "account extended public key".
- A wallet check takes the wallet's BIP39 passphrase only from a file, `--bip39-passphrase-file`, also together with `--ask-secrets`; the private screen and the menu do not ask for it.
- Every answer of the menu that is no secret can be given as an option of its command. Among them: `--scan-gap`; `--max-candidates` for `sskr-combine` and `sskr-export`; `--backup-check yes|no` for `encode` and `sskr-split`, which also takes `--heir-sheet` and `--heir-sheet-size`; for `decode --ask-secrets`, the wallet options with `--bip39-passphrase-file`, `--encoded-fingerprint`, `--list-candidates`, `--max-candidates`, `--max-results`, `--max-tries` and `--input-kind codes|share`. A share typed into Decode takes Decode's wallet and limits to the restore. The menu's own wallet question offers every coin and the number of addresses too.
- Every feature has its self-test beside it: quick known answers before every command (BIP39 seed and master fingerprint, date patterns, codes and shares marked with `?`, the word search, the candidate list, wallet evidence and the address scan, coin addresses, the heir sheet, share cards), and its row in `mnemocode self-test` with the slower checks (the 24 English BIP39 vectors, date and word searches with a wallet, age-encrypted lists, share backup checks, shares repaired together and with dates, the heir-sheet and share-card PDFs, QR images beside a sheet). Known answers come from published vectors or from an independent implementation that first reproduces one, and every check also gets a case it must refuse. Each coin has a known answer before every command, and so does the check of a written backup, and every form of a phrase of 15, 18 and 21 words with MnemoCode Seedshift, beside those of 12 and 24 words without it. Before it splits or combines shares, MnemoCode also restores a set of shares of the 32-byte secret of a 24-word phrase, which an independent implementation restores without the share engine after it has restored the official BCR-2020-011 vector. The checks before every command take less than half a second: the valid last words of a phrase are found from its entropy, without validating 2,048 phrases.
- The startup self-test also has independent answers for the valid last words of the Original Seedshift at every phrase length, a check of PNG admission, and the colors of 40 card codes, which must stay apart.
- Before it splits or combines shares, MnemoCode also gives the SSKR engine a share whose group index is outside its group count, which the engine must refuse.
- `mnemocode self-test` also checks the search of codes with `?` ("Marked codes search"), the writer of candidate lists (in "Candidate lists"), the split into shares and their restore ("Share split and restore"), and card PDFs read back as drawing steps ("Card pages read back"). Each of them has a case it must refuse.
- A date search finds each phrase once. Seedshift adds the year to a word number modulo the 2,048 words, so the same phrase would come back with the year 2,048, 4,096 and 6,144 years later; each set of shifts is tried once, with the earliest dates. That holds also where the day of the latest date moves only part of the last word, at the most dates a phrase takes, and the search keeps nothing of the combinations it tried, so that one of two billion needs no more memory than a small one. Its time is told from a phrase of its own length.
- A record of the Original Seedshift with a replaced last word finds its 128 or fewer last words from the entropy rather than by trying all 2,048.
- Several phrases restored from shares are numbered "phrase 2 of 3" and, on the private screen, shown one screen each, the next on Enter.
- In the menu, finding a forgotten date digit asks how to recognise the wallet: by its fingerprint or an address, whose coin is chosen from one list of every coin, as mhfe asks it, and after an address among how many to look; with the Original Seedshift it may be left out. `recover-date --ask-secrets` asks for it after the dates when the mode needs one and no option gives it.
- Decode and Restore from Shamir shares take `?` for a forgotten digit of a date on the private screen, in Restore also together with `?` in share codes, and search the dates as `recover-date` does. Where every date gives a valid phrase they ask for the wallet's fingerprint or one of its first receiving addresses, and Restore shows the share and date combinations and their time before it searches. Decode asks for the wallet with the original Seedshift too, where it may be left out.
- On the private screen, Decode, the search for a forgotten date digit and Restore from Shamir shares show the encoded fingerprint, the fingerprint of the masked phrase that Encode and the split print, as soon as the codes or complete shares are read: a code written down or typed wrongly shows before the dates are typed. Encode and Decode show it by one rule: whenever the codes are a valid BIP39 phrase, which the Original Seedshift's are only by chance.
- On a terminal, the result of Decode and of Restore from Shamir shares gets a screen of its own: the questions and the search are cleared away, and each part stands apart under its label. The original seed phrase is numbered, four words to a row as `mhfe` shows a phrase, with a line to copy below it, and each fingerprint stands under the phrase it belongs to: the encoded one under the masked phrase (decoy), the original one under the seed phrase. Restore lists the elements it filled in as a table, a row for each share, and the progress of a search stays on one line.
- On the private screen, `decode` asks for codes without an MNC1 header whether Seedshift was used and which one, and `recover-date` which Seedshift; Decode in the menu passes the answer on as `--mode`.
- Direct mode takes no dates: dates given with it are refused, for codes and for shares.
- When nothing tells which of two shares is wrong, such as two that carry the same share number but differ, both are named and the person chooses which to change or leave out. The written-backup check uses a share given twice once, as Restore does.
- `recover-date` accepts `?` for each forgotten digit and up to three incomplete dates. Identical patterns are not tried twice, and a limit stops a search that is too large before it starts. Every search of the dates or of marked shares that takes longer than 12 hours on the computer is asked for first; `--max-candidates` and `--max-tries` allow one from the command line.
- Decode takes codes with `?` where they cannot be read, on its private screen, through the library part `mnemocode/core/missing-codes-search`, which another host drives the same way: a word number, a word, a Unicode code or a whole color, narrowed by a few letters (`ab*`), words joined by `|`, or a `?` for one digit. It finds them by the encoded fingerprint that Encode showed, without the dates; by the wallet's fingerprint or an address with the dates, which may hold `?` too, so that codes and dates are found together; or lists them where they are few. It says how long the search takes, and shows the codes and dates it found.
- In colors, Decode names the words that a mark leaves open rather than codes.
- Unreadable colors of a record whose order tags start later than 0 are searched in every placement that the tags read allow. The unknown places of each placement are named, such as "Words 1 and 2 or words 11 and 12".
- Decode's joint search of unreadable codes and forgotten date digits counts each phrase that passes the wallet check once. Two different phrases, which a fingerprint lets through by chance, give several sets, not one found. One phrase that several sets of codes and dates give is found, with "N sets of codes and dates give this phrase; those found are one of them, so keep the dates you used."
- Decode offers to list the candidates of codes with `?` only where the list can hold their phrases: with the Original Seedshift and a valid last word, each set of codes gives a phrase for every valid last word, and these are counted. Where they do not fit, `--list-candidates` gets one line that says why, and the way to search is asked. A list that overflows all the same says "More than 16 phrases fit these codes and dates." and asks for the way again, keeping the codes and dates typed.
- Where a fingerprint finds the phrase, `recover-date` and `decode` print the warning that a master fingerprint is only 32 bits and is a filter, not proof of recovery: after the matches, and after the codes found, also by the encoded fingerprint. `sskr-combine` prints it once, after the restored phrases, and `sskr-export` once, after the shares it saved, where a fingerprint chose them among the sets that fit.
- When more than 100 sets of codes with `?` fit, Decode says how many fit.
- A Shamir share typed into Decode or read from a QR code, complete or with `?`, is recognized: Decode goes on to the restore from shares with it as the first share and asks for the others; a share read from a QR code is shown as text, and the next can be read from another QR code image. Where the text could also be the codes, it asks which.
- Decode reads every share of a paste of several lines or of a text file, such as members 1 and 3 of a 2-of-3 set, and does not take the later shares for extra card codes. A line that cannot be read is named, to be corrected.
- Where Restore and the recovery entries ask for codes, shares or a phrase, a path of a local text file may be typed in the same field. A saved share file gives every share line, and an MNC1 record keeps its format and Seedshift. A file that cannot be read is asked for again.
- A date to search may hold a lone `?` for a whole day, month or year (`15-?-2025`), or for a whole date not remembered at all; a few values joined by `|` (`05|15-09-2026`). A date search may have up to 2,147,483,648 date combinations; Decode's joint search of codes with `?` and dates may have more. A search longer than 12 hours is asked for first.
- After Encode shows its result on the private screen, it offers to check the backup: you type it again from what you wrote down, with the dates, and MnemoCode says whether it restores the same seed phrase.
- The check of a written backup counts and places the codes in the form they were written in, as they were typed: a changed color is named by the place it was typed at, and a wrong count in the form's own unit, such as 12 words or 8 codes.
- Encode offers the original wallet phrase beside the shares as words, selected codes or both (`--show-original words|codes|both`). It is shown on the screen only; exported share files never hold it.
- `encode --sskr` shows the whole phrase beside the shares only with `--format`.
- Encode offers the English words after Seedshift beside the codes or shares (`--show-masked-words`). They are shown on the screen only, not saved with the shares.
- `encode --heir-sheet` saves one sheet for heirs, to print on both sides in A5 or A6 (`--heir-sheet-size`): what the backup is, room for a hint written by hand, the steps in the menu, and the basics for someone new to wallets. It holds no secret: no codes, no dates, no fingerprint and no places. [A guide for heirs](docs/HEIRS.md) explains the same in more detail.
- The sheet for heirs says how many words the seed phrase has, or how many codes each share has, so that the codes after them on printed cards are left out. `decode --words` and `recover-date --words` read only the codes of so many words from the start, also with `?` in Color Unicode codes, and the menu asks for the number when codes are typed. A decode whose checksum fails names the shorter starts of the codes whose checksum is valid, by their fingerprints.
- A share is read up to its own length, which its first codes say: codes typed after it, such as the extra codes of its cards, are left out, also after a share with `?` marks. A `?` on such an extra code carries nothing.
- The guide to recovery without MnemoCode says where the extra codes of printed cards are: the backup is the first cards by number, as many as the sheet for heirs says, and a color among the extra cards repeats an order tag. Cards in Color Unicode print each color as its six RGB digits, which the guide's RGB steps read.
- The word lookup entry of the menu saves numbered English and Traditional Chinese word lists, Unicode characters and codes, the complete mapping and a standalone English guide to manual recovery. Full set saves them together in one folder.
- `table --all --table-format … --output …`, `table --recovery-guide` and `table --word-lists-dir …` save the same files from the command line.
- A lookup takes one of `--word`, `--index` and `--unicode`; two of them are refused.
- A damaged candidate list is refused with the reason that age gives, such as a wrong tag, in a browser too.
- A candidate file larger than any list can be is refused before it is read or a key is asked for: "The encrypted candidate file exceeds the supported limit of 155292688 bytes.", or 155,189,248 bytes for a list without encryption. Its age header must have exactly one recipient with the usual lengths, or it is refused with "The age header is malformed."
- `--share-file` reads shares one per line or separated by `;`, as they are typed, and joins a share that is wrapped over several lines. A file that holds a seed phrase instead of shares is refused, as a typed one is. A share written with commas between its elements is read like one written with spaces.
- The type of a testnet address is described as "testnet, …", such as "testnet, Taproot (BIP86)", for every coin, Dash Core addresses included.
- When `recover-date` cannot show every candidate, it also offers to change the dates, as Decode does.
- A number given to an option is a whole number in plain digits; anything else is refused with "… must be a base-10 integer from …".
- Several refusals say plainly what is wrong:
  - A split: "A split needs a threshold from 2 to the number of shares, and at most 16 shares: with a threshold of 1 no share would be checked." `--threshold` and `--shares` outside that range are refused as numbers "from 2 through 16".
  - A `--mode` or `--format` that differs from the record: "The record was made with …, not with …." and "The record holds … codes, not …."
  - A share that does not fit with the others: "Share N does not fit with the others: with it they give another phrase or none. Leave it out, or check it."
  - `--list-candidates` and `--encoded-fingerprint` name their option: "--list-candidates: a list holds at most 16 candidates; …" and "--encoded-fingerprint: these codes keep no checksum, so their encoded fingerprint cannot tell them."
  - Codes that fit no form: "These codes fit no form of an encoded seed phrase.", as for codes with `?`.
  - An address of Bitcoin, Litecoin, Bitcoin Cash or Dash that is not the address of a single key: "it is not the address of a single key; only … can be checked".
  - Color Unicode with a code missing: "Color Unicode needs two four-digit codes for every color", with the numbers of codes allowed.
  - A candidate file that the Scanner key or the passphrase does not open: "This Scanner key does not open the candidate file, or its header is damaged (…)"; one whose contents only are damaged: "The candidate file is damaged (…)".
  - Lists of choices in messages have no comma before "or", such as "12, 15, 18, 21 or 24".

### Secret handling

- MnemoCode wipes its own byte copies of the phrase data after use, as far as the runtime allows; copies held by libraries and in JavaScript strings cannot be erased (SECURITY.md).
- These copies include the buffers of a parsed backup, of form detection, of shorter phrases, of colors and of text decoding, candidate indexes, terminal geometry, the page of the private screen, keys typed ahead, and recoloured card images and artwork. They are wiped also after a failure, and when Ctrl+C cancels a question or a search. Ctrl+C while a command works, such as while cards are drawn, ends the process at once without wiping them.
- Once a split or a restore returns, no copy of the secret or of a share stays in the WebAssembly memory of the SSKR engine, bridge package `recovery-sskr-wasm` 0.1.9. The bridge writes and reads the text of a share in buffers that it wipes, wipes a restored secret also when its SSKR digest fails or its copy to the host fails, and overwrites the stack where the SSKR library worked. It checks byte arrays, and the Node.js host checks thresholds and counts, before any secret is copied.
- A refusal names the field and does not repeat what was typed in it: a seed phrase pasted into a record mode, format, month, command, help topic or unknown option, a share that the SSKR engine cannot decode, a character of card text that the card font lacks, or a malformed age identity. Known options keep their usual labels.
- A phrase, record, share, date or original final word is refused as a command-line value (`--mnemonic`, `--input`, `--share`, `--date`, `--dates`, `--old-date`, `--old-dates`, `--last-word`), public test data included: "Secret material for … must not be passed as a command-line value." The refusal names the file option or `--ask-secrets` to use instead.
- Commands without the private screen read secrets from bounded local files or standard input: `--mnemonic-file`, `--input-file`, `--share-file`, `--qr-file`, `--share-qr`, and `--dates-file`, `--old-dates-file` and `--last-word-file`. Standard input supplies one material source per command.
- Nothing is saved over an existing file or folder. When the name given is taken, MnemoCode saves under the first free numbered name, such as `cards-1.pdf`, without spaces or brackets that a shell would read, and says so after saving; the name is settled before the seed phrase is asked, so a taken name never stops a command. A result named like an input of the same command is refused.
- Every saved file, Shamir shares included, appears under its name only when it is complete. MnemoCode writes it to a private temporary file first and then gives it its final name in one step, without ever replacing an existing file. On memory cards and USB sticks formatted with FAT or exFAT, which cannot give a file a second name, an empty file holds the name until the complete one replaces it, and is removed again if that fails.
- A save that fails says why it failed, also when its reserved folder was removed meanwhile. When its private staging folder cannot be removed, after a failed save or a successful one, MnemoCode names the folder, says that it may hold a copy, and asks to delete it.
- Text, standard input and QR image files are read up to their size limit and no further, also when they come from a pipe or keep growing, whatever size the system reports.
- A QR code image may have up to 8 megapixels, a whole 3840 x 2160 screen, and up to 8 bits per sample; a larger image, or one with 16-bit samples, is refused before it is decoded, so that a small file cannot make the decoder take more than about 200 MiB.
- Before a QR code image in PNG is decoded, MnemoCode checks its start, its header and the size of its image data, interlaced images included. A damaged start or a second header is refused with its reason.
- A QR code image read as input (`--qr-file`, `--share-qr`) is wiped from memory once its code is read, also when it is refused, as text input is: MnemoCode's own copies of the file's bytes and of its decoded pixels. The copies inside the decoding libraries and the decoded text, a JavaScript string, cannot be erased.
- MnemoCode's own byte copies of what is saved of a backup, the record, the shares as text, card PDFs and images and QR images, are wiped from memory once the file is written or refused; JavaScript strings, such as the record text, cannot be erased.
- A typed answer can be edited as in a shell: the arrow keys, Home and End, Ctrl with an arrow, Delete, Ctrl+K and Ctrl+W, also when a long answer wraps onto further rows. At a prompt for a secret, the key after Escape is read as typed.
- Where a question takes words, the words that begin like the one being typed appear below it: after one letter how many there are, from two letters the words themselves, and a warning when no word begins like it. Tab completes the word as far as those words agree, and ends it with a space once one is left. This works for the seed phrase, the words of `recover-word`, a word looked up in the table, encoded seed phrases in English words and shares in Bytewords. The hints appear only where the typed text is shown, on the private screen and in the menu. A pasted Tab still separates words as a space does. The rule is one host-neutral module, `core/word-hints.ts`, which other front ends take as well.
- `--ask-secrets` works on Linux, macOS and Windows: MnemoCode reads the answer itself. Backspace and Ctrl+U edit it. Keys typed or pasted before a question appears do not answer it. A paste of several lines is one answer: words, codes and dates may come one per line, and shares pasted one per line count as separated by semicolons. A wide character at the right edge wraps onto the next row as the terminal wraps it.
- No command ends because of a wrong answer. On the private screen each answer is checked as soon as it is given, and what can be checked before the dates, such as the record header, the mode, the form and the checksum, is checked before they are asked. An answer that cannot be used is explained in one line that names at most its place, such as "Date 2" or "Share 3", and asked again; the other answers are kept. A share that cannot be read is typed again alone, and an empty answer is asked again with a hint. A result that cannot be used, such as dates that give no matching wallet or shares that restore nothing, offers what to change. Only the person ends a command early, with Ctrl+C ("Cancelled.", exit code 130) or by choosing Stop, apart from a failed self-test; while a secret is typed Escape does nothing, and at a visible value, such as a fingerprint, an address or a file name, it goes back to the question before.
- Ctrl+C while a command works, such as while card images are drawn, removes the temporary folders of the export, which hold private copies, and an output folder that the export is still filling. It names any folder it cannot remove, says `Cancelled.` once and ends with exit code 130, as Ctrl+C at a question does. A second Ctrl+C does not cut that cleanup short.
- When a file cannot be saved after the result is shown, for example on a full disk, the result stays on the private screen, one line says why, and MnemoCode offers to try again, to use another name, or to skip it. The QR code image saved beside a sheet takes the same offer. Shares are shown even when saving them fails.
- A command that asks for a secret runs on a private screen of its own in the terminal: what you type is shown there, and so is the result. When you press Enter, the screen is cleared, so that nothing stays in the scrollback; output sent to a file or a pipe goes there.
- With `--ask-secrets`, `decode` and `recover-date` take the record from `--input-file` or `--qr-file` and ask only for the dates. `sskr-combine` and `sskr-export` refuse dates given on the command line with `--ask-secrets`, as the other commands do.
- An on-or-off option given a value, such as `--missing-word yes`, is refused by every command.
- In a terminal that says `TERM=dumb`, which cannot clear its screen, `--ask-secrets` says so, and a start without a command shows the help with that reason.
- Text read from a QR code image is shown without its control characters, so that an image cannot move the cursor or erase a line on the private screen.
- Every run is protected as far as Node.js allows: core dumps are off on Linux and macOS, and MnemoCode runs under the Node.js permission model. That model allows no network, and a command that does not need them cannot write files or start other programs. The single executable starts under the model by itself, and each entry of the menu runs in a process of its own. A caller that already runs MnemoCode under that model keeps the rights it granted on purpose, such as `--allow-net`. The library has the rights of the program that uses it. Node.js enforces the model, not the operating system, so it is not a sandbox.
- Re-encode with `--ask-secrets` and no option of the new backup, as the menu runs it, keeps the rights to write files and start programs until the old backup is read and its phrase confirmed. Then the permission model gives up those that the answers do not need, while the system's limits keep what they allowed at the start.
- Below the permission model the operating system enforces what it can, with the same needs of each command. On Linux, seccomp refuses new sockets and, where a command starts no program, starting one; Landlock refuses file writes where a command saves nothing; both hold for every thread, on kernels that can apply them to all threads at once (Landlock needs this in a newer kernel, such as Linux 7.0). On macOS no debugger can attach, and the system sandbox refuses the network and, where a command starts none, other programs. On Windows crash reports leave out the heap, extension DLLs and DLLs from network shares are refused, and a job object refuses other programs. Each limit is confirmed before it is named: on Linux and by the macOS sandbox by trying what it forbids, on Windows by reading it back from the system; macOS confirms that no debugger can attach only by accepting the call. What a system does not offer is left out without a refusal, and the self-test says what was not available and why.
- Before a secret, MnemoCode warns when swap is not encrypted (Linux) and when a file would be saved into a folder that a cloud service synchronises.
- Run from source or from the package, MnemoCode compares the SSKR engine's files with fixed SHA-256 hashes before any secret. A damaged list of hashes gets the same refusal as a changed file, "SSKR dependency integrity check failed. No secret was processed.", and a later attempt with sound files goes on.
- The random numbers for shares come from Node.js `crypto.randomFillSync`.
- Before a candidate list is encrypted, MnemoCode checks the encryption with fast known answers; for the Scanner's key it checks X25519 too. Nothing is encrypted after a failure. Before it asks for a list's passphrase, it checks the symmetric encryption without WebCrypto. The slow scrypt known answers run in `mnemocode self-test`.
- PNG and JPEG export runs only a `pdftocairo` found by its full path in a folder of `PATH`, never one in the current folder or in an empty or relative entry of `PATH`, which Windows, and Linux for an empty entry, would otherwise run first. On Windows it looks for `pdftocairo.exe`, reads a quoted entry of `PATH` without its quotes, and skips an entry without a drive or a share. Each page is drawn in the private temporary folder.
- On Linux the temporary files of PNG and JPEG export stay in memory (`/dev/shm`) where it can be written; otherwise they go to the system's temporary folder, which is usually on the disk.
- The folder that holds the separate cards of one Shamir share can be read only by your user account, like the other export folders, on file systems that keep Unix permissions (Linux and macOS); MnemoCode does not restrict Windows ACLs or FAT and exFAT media.
- A command refuses an output folder that cannot be written before it asks for a secret, as the menu does. An output given as `-` or left empty is refused with "The … needs a path; - and empty paths are not accepted."

### Card exports

- The QR code that `--card-qr` prints on the sheets is also saved as a PNG image where they go: beside the PDF, or in the folder of the images or card files, one image per share for Shamir shares. Decode reads it back with `--qr-file`, Restore with `--share-qr`.
- Every collection, including A4, is one page laid out as a design proposal.
- A collection sheet has a centred heading and the slogan in the bottom line. Business cards lie on a dark page with a grey world map, and material samples on a backdrop of their own setting.
- A material sample shows a colour that the material is really made in, near its reference, laid over the image. Two different codes never get the same sample on one sheet.
- The optional QR code of a collection has its own corner on the same page. No separate QR page is made.
- Individual cards have no QR code.
- In the menu, "Also as printable cards" asks two questions about the files: which kind of file, PDF, PNG or JPEG, saying at once when images need `pdftocairo` and it is missing, and then how the cards are laid out, on A6, A5 or A4 sheets in one PDF or as images of the sheets, or as separate business cards in a new folder. For sheets it asks whether to add a QR code with the codes of the backup, without the extra cards, and for all cards whether to type your own details. The names and details on cards are a decoy, random unless typed.
- The menu offers printable cards with a choice of design for shares in colors and Unicode codes.
- Separate cards are named after their number and code, such as `01-1EAB91.pdf`, without spaces.
- `--page-size business` gives separate numbered cards, one per page. `a6`, `a5` and `a4` give one sheet, and `a6` is the default for every template, share sheets of every design included.
- The A5 page size, 148 × 210 mm, gives one sheet, as A6 and A4 do.
- Separate cards of a 24-word phrase keep the size of a business card.
- Images are made with the Poppler program `pdftocairo`. The rounded corners of a separate card are transparent in PNG.
- Separate business cards print their number before the code. No card prints the size of the set.
- Invented email and website addresses end in `.example`, so they cannot belong to a real company.
- `--cards-dir` is refused together with a sheet size.
- Each Shamir share has its own page, and a QR code holds exactly one share.
- Other programs can render the same cards through the `mnemocode/cards` entry point, which has no Node.js dependency. A card session keeps the same invented person, company and studio for every export of one working session.
- Text on business cards is aligned with its icon or logo, and a role keeps its distance from the name above it.
- In the card design "Signature curves" the company name stands above the logo, so that the curve does not run under the name.
- Every text on a card, your details, the studio name, the slogan, subtitle, footer and reference label, is one line without control characters or Unicode line separators, and at most 100 characters as it is drawn, in NFC and trimmed.
- A long reference label on a separate card of the IT design shrinks to fit, and one too long to read there is refused rather than running off the card.
- Share cards whose details cannot fit are refused before any secret is asked.
- Codes written as Unicode codes (format 3) have cards, for the phrase and for its shares: one code to a card: on A6, A5 or A4 sheets in every template, and as separate cards in the business card designs. Shares in Unicode codes are not printed with the enclosure and tile materials, which have too few samples for the longest share. The color of a card only decorates it: one code always has one color, and the different codes of a set get colors that look as different as possible on every design, compared in OKLab as each design shows them. Card export requires format 3, 4 or 5.
- Shares written as word numbers, Bytewords or a `ur:sskr` code have no cards; shares in colors or Unicode codes print one code to a card. Cards of shares in another form are refused before a secret is asked: "Shares written as words have no cards: cards print shares in colors or in Unicode codes."
- A sheet ends with a few random codes that belong to nothing: at least one, then as many as fill every row. It has at least three rows where they fit, not two long ones, with the largest cards that fit on one page, and of cards about as large the most of them, so that its cards fill the page in height and width. The rows share the height evenly, above, between and below them, and the QR code sits higher, in the corner of the heading. Without `--orientation` a sheet is turned the way that gives such a sheet. Separate cards add exactly one decoy after all real codes, including for each Shamir share; a PDF, its images and its card files of the same layout show the same cards. The QR code holds only the real codes.
- Business cards take the brightness of their color as well as its hue, and a wider range of its saturation, so that pale, deep and dark colors of one set look apart. The curves design chooses its ink by the brightness too.
- Every card holds one code. There are thirteen templates.
- `preview` draws a new sample phrase for each run, from the computer's randomness, masked with public dates, so that its cards show colours as varied as a real backup's.
- `preview --list` numbers the designs as `--template` takes them. `preview --all` at a card size refuses a design printed on sheets only before it draws any.
- Saved PDFs carry no document information: no creation or modification time, no producer.
- The QR code of a sheet is at least 12 mm wide, so that its caption fits under it.
- A long name under a sample, such as the name of a finish, takes two lines at the size of the sheet rather than shrinking into small print, in every design. The line with the number and the code always stays whole.
- The concrete panels, wall tiles and parquet behind material samples are laid out around the samples: their joints run between them, and every sample sits in the middle of a panel or tile of its own, on every page size. The holes of the form ties sit where the joints cross, between the samples.
- The object in each material image, a tile, a switch plate, a kitchen front or a hood, sits in the middle of its sample.
- The colour of a material sample is laid only over the object in its image; the backdrop, shadows and screws keep their own colour.
- In the menu, sheets ask how they are turned: landscape, portrait, or whichever fills the sheet best (`--orientation`; without it, at least three rows where they fit, then the largest cards).
- A new folder for cards or images may not have a name that ends in `.pdf`, `.png`, `.jpg` or `.jpeg`, which would later stand in the way of a file of that name. A file whose name a folder has is refused with "A folder has this name; give the file another name, or a name inside that folder."
- After shares are saved, one note says how many of them restore the phrase, or with Seedshift only the masked phrase, and where each share is in what was saved.
- Separate sample cards show one design: `preview --all --cards-dir` is refused with "Separate sample cards show one design: choose one design.", before the folder is checked.
- Separate cards are made in the business card designs only. A design of material samples is a collection that only its sheet shows, with its backdrop and QR code, so it is printed on A6, A5 or A4 sheets; separate cards of it, `--cards-dir`, `--page-size business` or `--card-layout individual`, are refused before any secret is asked, and the menu offers only the business card designs for them.

### Library for other programs

- Each part of the library, such as the date search, the share set or the wallet check, has an entry point of its own without Node.js code, such as `mnemocode/core/date-search`. Another program, a browser page for example, takes only the part it needs and passes what only it has, such as its PBKDF2 or its SSKR library. A long search, or the assessment of a share repair, stops at the host's signal and gives what it found before the stop, marked as stopped, rather than failing. [Source layout](docs/ARCHITECTURE.md#modules-for-other-hosts) lists the parts.
- More parts of the library have an entry point of their own: `mnemocode/core/candidate-list-writer` writes a candidate list as the command line does, `mnemocode/sskr/share-restore` takes a page through the restore from shares step by step, `mnemocode/export/document-formats` names the kinds of card files, `mnemocode/export/card-drawing` reads the pages of card PDFs as drawing steps for a page without Poppler, `mnemocode/export/sskr-keeping-text` says how saved shares are kept, and `mnemocode/core/candidate-file-admission` checks the size and the age header of a candidate file before a host reads it in full or asks for its key.
- A library entry, `mnemocode/core/re-encoding`, holds the rule of `re-encode` for other programs (`ReEncoding`), which keeps a copy of the confirmed phrase of its own.
- `MnemoCodeSelfTest` takes the checks of the features a host builds in (`features`, `MnemoCodeSelfTest.core(features)`) and optionally the host's PBKDF2.
- The self-tests of the search of codes with `?`, of the candidate list writer, of the split, of the restore from shares and of the card PDF reader have entry points of their own: `mnemocode/core/missing-codes-search-self-test`, `mnemocode/core/candidate-list-writer-self-test`, `mnemocode/sskr/split-self-test`, `mnemocode/sskr/share-restore-self-test` and `mnemocode/export/card-drawing-self-test`.
- The refusal cases of the SSKR known answers, which run before shares are split or combined, accept only the refusal of a combination, `ShareCombineRefusalError` (`sskr.engine.combine`), whatever its words. A host's SSKR library refuses with it; any other error fails the check.
- Every refusal carries a stable code of its module beside its message, error kind and cause, from one shared error catalog, so that the terminal and a browser host tell refusals apart the same way.
- Each code stands for one condition, so that a host can choose its own words from the code: `core.address-scan` `first-index-refused` and `address-count-refused`; `core.colors` `hashed-colors-refused` and `joined-colors-refused`; `sskr.repair` `too-many-marks-for-form` and `no-share-fits-marks`; `sskr.share-set` `too-many-combinations-open` and `combine-refused`; `sskr.transport` and `export.sskr-keeping-text` `shares-of-different-sets`, `member-given-twice` and `group-thresholds-conflict` (`SET_CONFLICT_CODES` of `sskr/set-topology.ts`); `core.backup-check` `too-few-shares`, `too-few-after-copies`, `shares-not-restorable-together` and `shares-do-not-restore`. The texts are those of the command line.
- The SSKR engine names its two share encodings, `ShareEncoding.CompactUr` and `ShareEncoding.Bytewords`. Its refusals name no host: "SSKR requires exactly 32 bytes of fresh randomness." and, for either encoding, "Enter at least one SSKR share." Its failures carry stable codes.
- The SSKR engine reads a compact UR in ASCII only, so U+212A KELVIN SIGN does not stand for k. `readShare` canonicalises a typed share before it reaches the engine.
- `ShareSplit` refuses a seed that the host's `fillRandom` left all zeros, before any share is made (`sskr.split.randomness-left-seed-unfilled`). `fillRandom` fills the buffer in place from a cryptographic source; what it returns is not read.
- The split's own check, the check of written shares and the restore tell refusals of the shares from failures of the host: `ShareSet.isRefusal` and `ShareBackupCheck.isRestoreRefusal` say which. A failure of the host's combiner passes through. A combiner that returns a secret of a length that no phrase has gives `sskr.split.sskr-generated-shares-did-not-reconstruct-source-entropy` (`isNoPhraseSecret` of `sskr/complete-shares.ts`).
- `ShareRestore.restore` and its repair publish nothing once their `ShareInput` has ended during a later step of the host, such as the date search, the search of marked shares or the wallet check: they refuse with `core.secret-value.wiped`. An ended input is reported before a stop of the host. `ShareInput.assertLive` and `ShareInput.assertTypedAt` are the checks; shares repaired keep the input revision that the wallet check confirmed.
- The search of a joint repair plan whose assessment the host stopped is a stopped search. That of a plan refused for another reason throws its reason (`sskr.joint-repair.plan-not-searchable`). A stopped search is made anew each time, so that no caller shares its sets.
- `ShareSet.digestChecked` says whether an SSKR digest checked the phrase, and `RepairedSet` and the results of the joint searches carry `digestUnchecked`. `ShareSet.of` reads it from the shares too (`digestChecks` of `sskr/complete-shares.ts`), also where a set leaves the field out. `combineSskrShares` refuses a phrase that no digest checked (`sskr.shares.no-digest-checked-phrase`), and `uncheckedNote` says so.
- `DateMatch`, `DateSearchResult`, `MissingCodesFound` and `UnmaskedPhrase` carry the warning of the wallet check's match, `FINGERPRINT_WARNING` for a fingerprint. `askWallet` refuses a match whose path or warning is given and is not text (`core.wallet-check.malformed-wallet-path`, `core.wallet-check.malformed-wallet-warning`).
- A WIF that matches gives the public key of its key as what was derived, never the private key. What a match derives is never secret.
- A `CardSettings.presentation` that a host gives passes the card-text rule before anything is drawn (`checkedCardPresentation`); `""` hides its line, and `null` means none.
- `shareKeepingNote` counts each member once within its set and refuses shares of another set or with another threshold for their group, by the three set-conflict codes, and a packaging it does not know (`export.sskr-keeping-text.packaging-unknown`).
- The writers refuse what they cannot write: `EncodedForm.codes` and `formatEncoded` refuse indexes that are no BIP39 phrase, such as 2048, -1, 1.5 or a sparse array, in every form (`core.bip39-sizes.*`); a share format given as `null` is refused; a candidate list refuses entropy that is not whole bytes; and rendering no cards is refused (`export.render.no-cards-to-render`).
- `MissingCodesSearch.isListOverflow` tells the refusal of a list that overflows (`core.missing-codes-search.list-overflow`), which names phrases where one set of codes gives several. Codes with `?` in a number of colors that no phrase has are refused with `core.missing-codes.colors-seed-phrase`.
- Recovery results, wallet checks, dates, wallet places and card plans that a host keeps own their secret bytes, which `wipe()` and disposal clear. The callers that make them clean up after cancellation, failed callbacks and failed saves; borrowed inputs and plans copied apart keep lifetimes of their own. Strings returned earlier and copies inside the runtime cannot be erased.
- A share assessment cancelled at its final callback gives no live repair plan.
- A repair of one share checks its listing limit before it enumerates candidates.
- Word-hint lists keep the snapshot that was checked, even when the caller's getters change.
- Card PDF readers that a host reuses have explicit operations to end them and to hand over their images; the one-shot reader hands over its live image buffers as it closes its cache.
- Candidate encryption runs its fast known answers once before its first use, refuses after a failure and lets a later call try again. An explicit recheck replaces an earlier success and holds new operations and late results until it passes.
- The doc comments of the published modules say what each value owns or borrows, its units, and what each function refuses under which code, the parsers of records, page sizes, orientations, image and document formats, colors, missing words and shares included.
- A module exports only what a code path uses. Hosts that compile the source modules take `HEX_ACCOUNT_BYTES` from `core/coins/address-sizes.ts`, `renderSskrPdf` and `SskrRenderOptions` from `export/sskr-render.ts`, `IMAGE_FORMATS` and `isImageFormat` from `export/document-formats.ts`, `CardPageSize` from `export/card-settings.ts`, `qrSizeForModuleMm` with `MIN_MODULE_MM` from `export/card-qr.ts`, `planJointRepair` from `sskr/joint-repair.ts`, and `PUBLIC_MNEMONIC` with the other public self-test values (`PUBLIC_FINGERPRINT`, `MASKED_DATE`, `MASKED_ENGLISH`, `MASKED_NUMBERS`, `ENCODED_FINGERPRINT`) from `core/self-test-vectors.ts`. `KECCAK_ACCOUNT_BYTES`, `pdfColor`, `qrSizeMm`, `MaterialPageSize` and `planShareRepair` are not exported, and `mnemocode/core/master-fingerprint-self-test` does not export `PUBLIC_MNEMONIC`.
- `WalletEvidenceCheck.prepare` gives a `PreparedWalletEvidence` typed by its match. `ShareInfo` is defined in `sskr/share-layout.ts` and `CardDrawing` in `export/drawing-sources.ts`; `sskr/transport.ts` and `export/templates.ts` export them too.

### Toolchain and dependencies

- The development runtime is Node.js 26.10.0.
- The development dependencies include Vitest 5.0.3 with its V8 coverage provider, TypeScript 7.0.2, Prettier 3.9.9, tsx 4.23.15 and `@types/node` 26.6.4.
- The SSKR engine is built here from its Rust source, offline in a pinned container (`pnpm build:sskr`), with Rust 1.99.0, wasm-bindgen 0.2.129 and current crates. A release builds it again and checks that the bytes are the same.
- pnpm 12.8.1 is pinned, and records its own release in the lockfile.
